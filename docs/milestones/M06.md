## 2. Goal and boundaries

**Observable result.** Documents and their ordered parts are written through ChangeSets with deterministic order keys, exact text under a declared encoding contract, and evidence associations to source versions. Authenticated readers list documents, inspect the parts they may read, reconstruct a document at head or at an old revision as a compact authorized projection (no hidden IDs, headings, positions, counts, or placeholders), search part text lexically, and export authorized text. Code-like parts are labeled as excerpts unless the part itself is a declared complete unit. Rendering output is Markdown or plain text produced server-side from authorized parts only, with a documented safe subset. The `scoped-document` fixture yields the golden views for two reader populations.

**In scope.** Order-key contract and validation; document and part write validation in ChangeSets; document routes (list, detail, parts, reconstruction, render, search, history, export); text encoding and digest contract; evidence selectors on parts; the fixture and golden outputs; safe Markdown rendering rules.

**Out of scope.** Nested parts (flat ordered parts only in the MVP; the spec makes nesting optional and core has no parent predicate), rich collaborative editing, binary documents, browser rendering to HTML (M12), topical context selection (M07), source-code ingestion formats (M08).

**Invariants touched.** AGENTS.md §5.3 (only authorized text reaches a renderer or consumer; hidden data never influences matches, counts, snippets), §6.2 (deterministic ordered parts, compact omission, excerpts never masquerade as complete code), §5.2 (current bindings on historical parts), §9 (ingested text is data, never executed or fetched).

## 3. Decisions to resolve

| ID | Decision | Rationale, evidence, proof obligation |
|---|---|---|
| D1 | **Order keys.** `c1:orderKey` is a rank string over `0-9A-Za-z`, length 1–64, never ending in `0`. Producers may supply valid keys. Sort by `(orderKey, canonical part IRI)`, including when independently protected parts have equal ranks. Equal ranks are valid: rejecting a collision with an unreadable sibling would reveal its hidden rank through validation. Invalid grammar gives `C1-DC-002 invalid_order_key`; duplicate resource identities remain invalid. `c1.documents.order.between(a, b)` returns a key strictly between neighboring ranks when one exists and otherwise raises an explicit exhaustion error. Finite 64-character keys cannot provide an unbounded insertion guarantee; callers may choose a new valid rank or make an authorized multi-part reorder. | Architecture §10.1 requires deterministic order without assuming whole-document renumbering; PLAN M06-T06 requires invalid ordering rejection, not globally unique raw ranks. ADR-0015 records the privacy conflict and refinement. |
| D2 | **Structure and nesting.** Parts are flat. `c1:partKind` values are a closed set validated in M06: `text`, `heading-1` … `heading-6`, `code`, `code-unit`, `quote`, `list-item`, `table`, `metadata`. `code` and `code-unit` may carry a language after a colon (`code:python`). `code-unit` asserts that the part's text is one complete source unit as declared by the producer; `code` is an excerpt by definition. A part's `partOfDocument` must reference a Document that exists at the ChangeSet base or is created in the same ChangeSet and is readable by the author (`C1-CS-010` otherwise). Moving a part is a `replace` changing `orderKey`; moving a part to another document is a `replace` changing `partOfDocument` and requires `contribute` on both documents. There is no cycle case because nesting is unsupported; a request that includes a nesting predicate is rejected as undeclared (`C1-IX-011`). | Spec §4.4 (nesting optional; ambiguous ordering rejected), §11.5. |
| D3 | **Text encoding contract.** `c1:text` is a Unicode string; C1 stores code points exactly as supplied (no NFC/NFKC, no newline normalization, no trailing-whitespace trimming); allowed control characters are `\t`, `\n`, `\r` (`C1-DC-003 control_character` otherwise); maximum 256 KiB per part (`C1-DC-004 part_too_large`). Responses include `text_digest = sha256(UTF-8 bytes of text)` computed on read, and `text_length` in code points. `Document.contentDigest`, when supplied by a producer, is its own claim about the complete source and is returned only to readers of the Document record; C1 never recomputes or verifies it against a partial projection. | Architecture §10.1 "declare text encoding, newline preservation, and digest rules"; PLAN M06-T05. |
| D4 | **Bindings and inheritance.** A `create` of a part defaults to `inherited_from = partOfDocument` when neither `scope_id` nor `inherited_from` is given; an explicit `scope_id` makes the part independent (M03 semantics). Re-scoping a document cascades to inheriting parts (existing M03 operation). Reading a Document record never grants its parts; reading a part never grants the document. A cross-document content move preserves the current scope and security inheritance source; a later re-scope of that original security parent still cascades. A separately authorized part re-scope can detach inheritance; ordinary moves and restores cannot activate new bindings. | Spec §4.4 "current security defaults can apply to its parts unless an explicit authorized binding differs"; ADR-0009. |
| D5 | **Compact authorized projection.** `GET /v1/documents/{id}?revision=` returns `{document: <record fields the reader may see>, parts: [ordered readable parts with text, kind, title, order_key, text_digest, text_length, part_id]}`; nothing else: no total part count, no omitted markers, no positions, no order-key gaps analysis, no `complete` flag for the document. Readers who cannot read the Document record but can read some parts receive 404 for the document route (a document is the anchor); `GET /v1/documents/{id}/parts` lists the same readable parts as a paged list. Parts are fetched through the M05 authorized selection (candidates filtered by `partOfDocument`), so hidden parts never enter ordering or counting. Historical revisions use the same current bindings. `GET /v1/documents/by-id?document_id=` provides the same detail projection without path-suffix ambiguity for arbitrary supported canonical IRIs. | Spec §4.4 compact projection, §6.4; PLAN M06-T01/T02/T04. |
| D6 | **Rendering.** `GET /v1/documents/{id}/render?format=markdown|text&revision=` produces text server-side from the same authorized part list: `heading-n` → `#`×n + escaped title or text; `text`, `quote`, `list-item` → Markdown with these escapes: raw HTML tags and entities are escaped (`<` → `&lt;`), autolinks and reference-style link definitions are neutralized (URL colons and Markdown link delimiters are escaped as inert display text), images are never emitted; `code` and `code-unit` → fenced blocks with the language tag and an info line `excerpt` or `complete unit` derived from D2, fence length chosen longer than any backtick run inside the text; `table` and `metadata` → fenced `text` blocks. The `text` format emits parts separated by exactly one blank line with no markup. No external resource is referenced or fetched; rendering never states that the document is complete. Rendering output is deterministic for identical input and authorization. | Spec F09 "labels cannot inject executable HTML/JavaScript, fetch arbitrary resources, or issue commands"; architecture §10.4; PLAN M06-T07. |
| D7 | **Search.** `GET /v1/documents?text_contains=&title=&kind=&revision=&limit=&cursor=` and `GET /v1/documents/{id}/parts?text_contains=`: `text_contains` is an exact substring match on NFKC-casefolded text (the same normalization as label prefix matching) of readable parts and titles; a document matches when at least one of its **readable** parts or its readable title matches; results list matched part IDs and a `match` explanation naming only readable parts; no snippets are generated. Counts are computed over the authorized selection. No stemming, tokenization, ranking, or synonym expansion exists. | Spec F02 "label/alias literal or prefix matching", A14 "search"; PLAN M06-T03. |
| D8 | **Evidence on parts.** Evidence about a document's text uses `oa:hasSource` = the DocumentPart IRI, `c1:sourceRevision` = the readable Document's `sourceRevision` (or the ChangeSet base knowledge revision for a native document), and an optional `Selector` with `selectorKind` `TextQuoteSelector` (`oa:exact`) or `TextPositionSelector` (`oa:start`, `oa:end` as code-point offsets within the part). Validation checks selector text/offsets and source revision against the staged part when it changes in the same ChangeSet, otherwise the base revision. The author must read both the part and its parent Document to substantiate its version; absent or unreadable references produce `C1-CS-010`, selector mismatch `C1-DC-005`, and version mismatch `C1-DC-009`. Evidence, selector, and part bindings stay independent; a reader of the evidence who cannot read the part sees its producer-copied excerpt only when that field is set and authorized with the Evidence. | Spec §4.3, §10.3 "immutable source versions and supported selectors"; [W3C Web Annotation Data Model](https://www.w3.org/TR/annotation-model/) selector definitions. |
| D9 | **Export and history.** `GET /v1/documents/{id}/export?format=jsonld|text&revision=` uses the M05 export boundary for the authorized document and part records (JSON-LD) or the `text` render; `GET /v1/history?resource_id=` (M04) covers documents and parts; `GET /v1/documents/{id}/history` lists revisions in which the document or any **readable** part changed, merging actual per-resource backend history under current bindings. One request plan preauthorizes the IDs, applied manifests conservatively narrow storage probes, and final current-security checks run after the captured knowledge-head check. Ordinary part replacements cannot remove the DocumentPart type. | Spec F10 export of permitted knowledge only; PLAN M06-T03/T04. |
| D10 | **Fixture `scoped-document`** (`fixtures/scoped-document/`): scopes `doc-public`, `doc-team`, `doc-legal`; principals `alice` (public), `bob` (public, team), `carol` (all three), `dave` (public only, later revoked from nothing but used as unrelated reader); document "Handbook" with parts: P1 heading (public), P2 text (public), P3 text (team), P4 code excerpt (team), P5 text (legal), P6 code-unit (legal), P7 text (public) — seven parts across three scopes; an unrelated document "Notes" entirely in `doc-legal` containing the term `zebra-token` that appears nowhere in Handbook; revision 2 edits P2 and moves P7 between P2 and P3 by changing its order key. Golden files: `expected/alice.json`, `expected/bob.json`, `expected/carol.json`, `expected/*.md`, `expected/*.txt`, `expected/search.json`, `expected/history.json`. | PLAN §4 fixture family; A14; G5. |
| D11 | **Layout and endpoints.** `src/c1/documents/` (`order.py`, `text.py`, `validation.py`, `service.py`, `render.py`, `search.py`), `src/c1/api/routes/documents.py`; ChangeSet validation hooks for document rules in `changes/validation.py` (D1–D3, D8). Endpoints: `GET /v1/documents`, `GET /v1/documents/{id}`, `GET /v1/documents/{id}/parts`, `GET /v1/documents/{id}/render`, `GET /v1/documents/{id}/export`, `GET /v1/documents/{id}/history`. Limits: 200 parts per page, 2000 parts per reconstruction (`C1-DC-006 document_too_large` beyond, explicit), 2 s budget. No new dependency; no Markdown library (the safe subset is emitted by C1's own template code, which is easier to audit than sanitizing a general renderer). | Architecture §3, §7 rows for documents. |

## 7. Recovery and security

| Failure point | Behavior |
|---|---|
| Producer ranks coincide after concurrent proposals | Both records retain their explicit rank and sort by canonical part IRI after the second proposal is rebased. A stale base still fails under the M04 ChangeSet rule; no silent renumbering occurs. |
| Reconstruction exceeds 2000 readable parts or the 2 s budget | Explicit 422/503 with no partial document presented as complete. |
| Rendering encounters an unknown `partKind` in old data | Treated as `text` with escaping; the request receives the ordinary audit entry; never executed or fetched. |
| Golden files drift | Regenerated only by an explicit command and reviewed in the diff. |

Secrets: none new. Rendering and search never contact the network; the test counter proves it. Hidden parts never reach the process's response assembly because selection is authorized first.
