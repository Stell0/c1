## 2. Goal and boundaries

Make upstream C1 installable and usable with an independently managed, pre-existing OIDC provider. C1 must not deploy, administer, or own that provider. Support self-hosted and externally managed deployments through the same public interfaces.

Users must be able to authenticate in the existing Explorer, enroll an explicitly approved initial administrator, administer C1 permissions independently of provider roles, create/read/review/modify authorized knowledge, run ordinary ChangeSet and Context Builder workflows, call existing APIs with validated user access tokens, and maintain/back up/restore C1 without owning the IdP.

NethServer 8 IdP is a reference integration target, never an architectural dependency. All reusable functionality belongs upstream; downstream modules consume released public contracts without private imports, bootstrap duplication, or source patches.

### Explicit exclusions and invariants

- No creation/modification of OIDC users, realms, tenants, or installations; no provider administrator credentials; no dynamic client registration. Registration is performed externally.
- No authentication proxy, Explorer replacement, separate agent-authentication protocol, agent-specific endpoints, or new delegation semantics.
- No provisioning of machine identities/service accounts in external providers; retain existing service-principal behavior and regressions.
- No arbitrary opaque-token fallback or automatic migration between identity namespaces.
- No mandatory AI credential, vector database, or M15–M18 capability.
- User-token operations remain attributed to the authenticated user and use current C1 permissions. `human` classifies the principal; it does not prove manual operation.
- Provider administrator roles, email, username, forwarded headers, unverified claims, and arbitrary `on_behalf_of` fields never confer C1 permissions. OpenFGA/current bindings remain authoritative.
- One shared repository, stable instance identity, independent review, current authorization on historical content, and fail-closed readiness remain intact.

### Responsibility boundaries

| Component | Responsibility |
|---|---|
| C1 | OIDC integration, token validation, stable principal identity, application initialization, enrollment, authorization, consistency, maintenance/recovery contracts. |
| External provider | Authentication, identity lifecycle/namespace, discovery, signing keys, supported claims, and token issuance. |
| Deployment supervisor | External client registration/instructions, configuration, service lifecycle, networking, TLS, secrets, persistence, writer quiescence, and backup transport. |
| Reference deployment | Bundled infrastructure/Keycloak provisioning and reference orchestration. |
| Platform integration | Adapt public provider-independent interfaces to a container deployment, Kubernetes operator, system service, NS8 module, or other host. |

### Versioned external OIDC configuration contract

Reuse existing `C1_*` conventions and protected secret files; introduce additional fields only for demonstrated gaps. Exact new names/schema versions are W1 deliverables, not currently executable settings.

| Setting | Purpose and compatibility rule |
|---|---|
| Issuer URL | Exact trusted OIDC issuer (`C1_ISSUER`). |
| Issuer alias | Stable internal identity namespace (`C1_ISSUER_ALIAS`); cannot silently change after installation. |
| Explorer client ID/secret | Externally registered confidential client; protected credential for the supported authentication method. |
| Redirect URI | Exact Explorer callback derived from validated deployment configuration and matched in external registration. |
| API audience | Expected access-token audience (`C1_AUDIENCE`), with a profile that cannot admit Explorer ID tokens. |
| Access-token profile | Explicit purpose, signature/algorithm, issuer, audience, subject, lifetime, and profile-specific required claims. |
| Principal-kind mapping | Explicit trusted claim-to-`human`/`service` mapping; missing/invalid legacy claim remains failure in the legacy profile. |
| TLS trust | System CA or configured private CA; preserve TLS verification and no-proxy/no-untrusted-redirect behavior. |
| Endpoint restrictions | Validated trusted endpoint policy, with explicit approval for differing origins. |
| Session settings | Expiry, idle/max lifetime, refresh capabilities, and documented logout behavior. |
| Continuity metadata | Stable instance/issuer-alias/identity-namespace binding and configuration-version compatibility. |

OIDC compliance alone does not establish C1-compatible access tokens. Require discovery, Code flow, S256 PKCE, a registered callback, supported confidential-client authentication, signed ID tokens, JWT API access tokens, trusted issuer/audience/subject, secure purpose identification, and principal classification. Unsupported providers fail with actionable errors rather than weaker validation.

Validate JWT signature, approved algorithm, exact issuer/audience, stable subject, `exp`, `iat`, and optional `nbf`; validate trusted discovery/JWKS. ID tokens never authenticate API requests. A verified signature or an untrusted claim alone cannot establish token purpose. Identity outages, discovery errors, and rotation failures must fail safely.

## 4. Work breakdown

### W1 — Define deployment-independent contracts

Inspect/reuse existing configuration, CLI, operational interfaces, and maintenance consistency checks. Qualify `state`, `consistency`, `guard-set`, `dr-verify`, and `dr-release`; expose only the minimum additional initialization/enrollment operations. Separate pure application administration from host orchestration.

Publish versioned input/output schemas, sanitized machine-readable JSON, stable failures/exit codes, bounded retries/timeouts, credential requirements, initialization/enrollment states, capability reporting, and compatibility/migration rules. Identify writer-stop/exclusive-backend requirements versus online-safe operations. Enrollment approval is a protected operator action, never ordinary runtime configuration.

Create a provider checklist for discovery, clients, audiences, claims, purpose, subjects, TLS, refresh, and logout. Resolve D1–D9 using source/pinned service evidence and record outstanding choices explicitly.

**Exit condition:** a deployment supervisor configures C1 through public documented interfaces without Keycloak or reference-Compose implementation knowledge.

### W2 — Decouple application initialization from IdP provisioning

Implement one initializer using already configured TerminusDB/OpenFGA endpoints. Initialize the core knowledge profile, workflow database/journal, OpenFGA store/model, stable application configuration/identifiers, and durable initialization state.

It must not provision users/clients/realms, request IdP administration credentials, manage infrastructure, or depend on Docker, Podman, Kubernetes, or NS8.

Refactor reference bootstrap into reference infrastructure/Keycloak provisioning followed by this same initializer. Preserve its supported operator interface; do not maintain separate database or authorization bootstrap logic.

Persist initialization intent **before** durable resource creation. Track instance ID/IRI base, exact issuer/alias and trusted namespace, API audience, database IDs, OpenFGA store/model IDs, schema/model versions, and completed steps. Expose empty, partial, awaiting-enrollment, complete, and incompatible/ambiguous states.

Serialize/reconcile after crashes, timeouts, and uncertain responses before creating new resources. Never reset knowledge, credentials, grants, stores/models, or persistent identity. Reject ambiguous ownership or incompatible state. Define how the intent and ownership remain discoverable when the workflow database itself is absent.

**Exit condition:** safe repeatable application initialization without identity-provider administration.

### W3 — Explicit first-administrator enrollment

1. A protected local operator approves an exact issuer/subject belonging to an existing provider account.
2. Record approval, bounded lifetime, and a durable enrollment guard; initialize required state without arbitrary grants.
3. Keep ordinary protected operations unavailable and normal readiness false. Permit only login/callback, required static assets, and enrollment confirmation through a C1-enforced setup allowlist.
4. The approved user authenticates through Explorer. Validate access tokens through the normal authentication contract; compare authenticated exact issuer/subject with the approval, never browser input or email.
5. Require explicit authenticated enrollment confirmation with CSRF protection.
6. Grant only instance `access_admin` and `schema_admin`, durably record completion, and reconcile interrupted/concurrent confirmation without duplicate/escalated grants.
7. Verify authorization/application consistency freshly before removing the guard.

Wrong identities, arbitrary first logins, and provider administrators cannot consume/replace approval. Define protected cancellation/replacement before completion and expiry behavior. Routine configuration cannot reopen completed enrollment; additional administrators use normal authorized administration. Approval/completion receipts and logs exclude tokens, client/session secrets, and confidential payloads.

**Exit condition:** exactly the approved external identity receives initial C1 administrative privileges with no first-login escalation path.

### W4 — External OIDC Explorer and API interoperability

Qualify the existing Explorer: discovery, login, state/PKCE, callback, signed ID-token audience/nonce, normal access-token validation, session creation, optional refresh, session/token expiry, local logout, optional provider logout, CSRF, secure cookies, and security headers.

Missing `end_session_endpoint` must not block local logout. Distinguish local logout, provider-session termination, refresh-token revocation, and already-issued access-token expiry; do not promise global invalidation. Keep Explorer cookies, refresh tokens, and client secrets private; no token export or separate agent interface is required.

Test at least reference Keycloak and an independently managed external provider with materially different settings, preferably a non-Keycloak implementation. C1 has no administrative ownership of the external fixture; test provisioning belongs to the supervisor. Record supported provider versions/token profiles/client registration/limitations.

With external identities: enroll administrator, create scopes, grant a least-privilege account, read permitted resources, deny unauthorized operations/administration, revoke and deny on the next request, run a full ChangeSet and Context Builder workflow, and require distinct submitter/approver when independent review is enabled.

**Exit condition:** real external browser login and ordinary authorized Explorer/API workflows without owning the IdP.

### W5 — Maintenance, backup, and disaster recovery

Qualify public application maintenance/consistency by reusing upstream operations; add only demonstrated gaps. The supervisor quiesces writers and handles database transport/storage/lifecycle. Define application-owned artifacts and explicit guard/verify/release procedures; see §7.

**Exit condition:** safe application-owned backup and fresh-node recovery without provider databases or administration access, verified namespace continuity, explicit authorization-snapshot acceptance, and fresh checks before release.

## 7. Recovery and security

### Initialization/enrollment failures

| Failure point | Required safe behavior and recovery |
|---|---|
| Intent persisted, resources absent | Retry from owned intent; no arbitrary grant, no ready state. |
| Resource created, response/step recording lost | Reconcile uniquely owned existing resource; never create duplicates or guess ownership. |
| Conflicting instance/issuer/namespace/model configuration | Refuse incompatible changes without rewriting persistent identity or knowledge. |
| Approval missing/expired/cancelled/wrong subject | Retain enrollment guard; only protected operator action replaces approval before completion. |
| Grant write/completion interrupted or concurrent | Reconcile exact approved grants and durable completion; no reenrollment or privilege widening. |
| Consistency/identity services unavailable | Keep guard/readiness false; bounded retries and sanitized actionable errors. |

The enrollment guard belongs in C1, not merely a reverse proxy. Normal protected operations remain unavailable. No bootstrap receipt or `force-ready` switch can establish readiness.

### External-provider backup boundary

Include knowledge/workflow storage, OpenFGA authorization persistence, stable instance identity/IRI base, required application configuration metadata, schema/model versions, namespace-continuity metadata, integrity information, and manifests.

Exclude external IdP databases, realms/tenants, users/password hashes, signing keys, and provider-wide admin credentials. Protect secret-bearing backup/configuration separately from diagnostic manifests. The supervisor is responsible for quiescence, backup transport, persistence, and environment-specific lifecycle.

### Restore and release sequence

1. Restore into an isolated, guarded, unpublished installation; verify checksums/completeness.
2. Check schema, profiles, authorization model, and configuration compatibility.
3. Preserve original instance ID/IRI base, issuer alias, and trusted identity-namespace binding.
4. Verify/reconcile restored knowledge, workflow, and OpenFGA consistency.
5. Reconcile external Explorer registration, including pairwise-subject/client continuity.
6. Establish evidence that restored subjects identify the same identities. Matching issuer text alone is insufficient after a namespace recreation. Routine signing-key rotation is not automatic namespace migration.
7. Require explicit operator acceptance of restored authorization snapshot; never silently treat old grants as current. Document reconciliation of later revocations.
8. Perform fresh consistency/identity verification before explicit guard release/publication.

Corruption, interruption, incomplete manifests, incompatible schema/models, inconsistent authorization, unavailable identity services, unverified namespace changes, or stale verification prevent release. Preserve guards until verification succeeds. Never remap principals by email/username or promise image rollback across incompatible persistent changes. Safe recovery preserves audit history and distinguishes application disaster recovery from knowledge-only compensating changes.

Protect TLS trust, discovery/JWKS, session/client secrets, and operator approval. No tokens/refresh credentials/secrets in receipts, normal logs, or public evidence. Validate untrusted data and rendering; use synthetic fixtures and exact signed/authenticated identities.
