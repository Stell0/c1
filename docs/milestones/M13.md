## 2. Goal and boundaries

**Observable result.** A release candidate, `c1` version `0.1.0rc1` (OD3), is built from one recorded revision into a locally built, digest-recorded OCI image. A reference Compose deployment:
- starts on a clean host from images already present;
- exposes only a TLS endpoint;
- runs every backend on an internal network with no Internet egress;
- reads its secrets from files;
- has a first administrator and nothing else.

On that deployment, an acceptance run completes the human and API workflows and every context profile with AI credentials absent. Backups are taken and restored in two modes:
- **knowledge-only:** current grants and bindings stay authoritative;
- **full disaster recovery:** the restored deployment stays unready until an operator verifies security freshness and releases it.

The candidate's full regression passes. The failure matrix is demonstrated. Limits are measured on a declared machine. Licenses and notices match the actual artifacts.

**In scope.**
- **Packaging:** a Containerfile for C1; the reference deployment in `deployment/reference/`; file-based secrets; a production first-administrator bootstrap; a TLS proxy.
- **Operations tooling** (`c1-admin`, a CLI in the `c1` package):
  - knowledge and security backup;
  - knowledge-only restore;
  - disaster-recovery restore, verify and release;
  - consistency check.
- **API description:** a generated `docs/api/openapi.json` and a route-parity test.
- **Documentation:** `docs/operations/` covering installation, API use, security administration, current-binding recovery, backup and restore, schema migration, import and export, and measured limits.
- **Releases:** third-party license inventory and `THIRD_PARTY_NOTICES`; `NOTICE`; the version bump.
- **Tests:** T01–T08 and the A01–A22 / G1–G9 acceptance matrix with automated cross-checking.
- **Measurements:** a benchmark harness and its results.

**Out of scope.**
- Publishing images or packages.
- Pushing a release tag.
- Deploying to production.
- NethServer 8 packaging.
- High availability, multi-process session sharing, online (hot) backup.
- Performance work beyond measuring. Any optimization needs its own plan (M14 benchmarks retrieval).
- Changes to authorization semantics or knowledge-model features.

**Invariants touched.** AGENTS.md §4.3 (restores never rewrite audit history), §5.2 (current bindings and fail-closed), §8 (licenses), §9 (no publishing or deployment).

| D6 | **Backups (OD2: quiesced).** `c1-admin backup --to DIR`:<br>1. Requires the C1 writer to be stopped (`c1` container down) and no pending operation in the journal.<br>2. Online backup is out of scope (OD2). **Proof (W1):** bundle and unbundle of a C1 knowledge database with full history preserves commit IDs and documents at fixture scale (software template), extending the planning probe. | D7 | **Knowledge-only restore.** `c1-admin restore-knowledge --from DIR`:<br>1. Requires `c1` stopped and no pending operation.<br>2. Checks that the backup's profile set is a subset of the current journal's installed set. If the backup lacks a profile installed later, the tool refuses, and the documentation describes the reviewed path: reinstall through a ChangeSet after restore.<br>3. Bundles the current knowledge database as a safety copy.<br>4. Deletes the knowledge database, recreates it, and unbundles the backup.<br>5. Appends a `KnowledgeRestore` record to the journal: backup manifest digest, previous head, restored head, operator, time.<br>The journal and OpenFGA are **untouched**:<br>• Resources in the backup without a current active binding stay denied (no binding means fail-closed).<br>• Resources whose binding was tightened after the backup follow the current binding.<br>• Historical-only resources keep their deny tombstones.<br>• ChangeSets applied after the backup keep their journal records. Their knowledge commits no longer exist at head, and their receipts remain as audit history.<br>The next ChangeSet needs a fresh base revision; stale ones are refused by the existing head check. | §15.3 ("A knowledge-only restore cannot restore old grants or bindings"); AGENTS.md §4.3 (audit history kept). | D8 | **Full disaster recovery (restore guard).** `c1-admin restore-full --from DIR --into <fresh deployment>`:<br>• Unbundles both databases and restores both Postgres dumps into a fresh, isolated deployment.<br>• Writes a `RestoreGuard` record into the journal before C1 first starts. `Runtime.ready()` returns false while an unreleased guard exists, so every protected request is 503.<br>`c1-admin dr verify` then:<br>(a) runs the existing journal recovery for pending operations;<br>(b) compares every journal binding with the live OpenFGA `bound_to` tuples (`FGA.scan_bindings`) and fails on any difference;<br>(c) reports the security backup time and the count of membership and instance tuples.<br>`c1-admin dr release --accept-security-as-of <ISO time> --reason <text>` records the operator's explicit acceptance in the guard and clears it. Memberships exist only in OpenFGA, so freshness cannot be proven automatically; the explicit, recorded operator acceptance is the guard. **Proof (T04).** |

## 7. Recovery and security

| Failure point | Expected safe behavior and recovery |
|---|---|
| Backup interrupted | No manifest is written, so the backup is invalid. Restore refuses a directory without a valid manifest and matching checksums. |
| Knowledge restore interrupted after the delete | The safety bundle from step 3 remains. The documented procedure unbundles it. C1 stays down: the tool exits non-zero, and readiness checks fail on a missing or mismatched profile registry. |
| Restored knowledge contains resources without current bindings | Denied, which is the existing fail-closed rule. Provisioning them needs the ordinary audited operations. |
| Disaster-recovery restore with stale memberships | Restore guard: unready until `verify` and an explicit, recorded `release`. Operators apply known revocations before release. |
| OpenFGA and journal disagree after restore | `verify` fails and release is refused. Repair uses the existing journal reconciliation or a re-provision; it is never forced. |
| Lost secret file or wrong permissions | Startup refuses with a safe message and no value printed. |
| Proxy misconfiguration exposing backends | Prevented by the internal network. T08 checks published ports. |

**Secrets.** Secret files live only on the deployment host, in ignored directories, mounted read-only. Backups contain secret-bearing data and are written mode 0600. Test certificates and keys are generated per run into ignored directories. No backup, certificate, password or token enters the repository or the evidence; the evidence records hashes, sizes and heads only.
