| Measurement | Laptop | makako (4 vCPU, shared) |
|---|---|---|
| Simple read, S / M | 0.23 s / — | 2.4 s / 2.7 s |
| Simple read round trips | 22–24 OpenFGA, 10 TerminusDB | the same |
| `graph-context` 64 KiB, S | 0.4 s | 7.2 s |

| Entity list over 4,500 readable resources (bench B3) | — | 21 s median, some 503s |

The same request makes the same calls on both hosts, but makako is about 10× slower. That is more than the hardware difference explains. M14a's counters record call counts, not where the time goes.

**Unmet M14a targets:**
- simple reads ≤ 2 s at S on makako (2.4 s);
- `graph-context` ≤ 6 s (7.2 s);
- single-create apply ≤ 5 s (30.5 s).

## 2. Goal and boundaries

**Goal:** remove the remaining fixed per-request and per-step costs, explain the makako gap with measurements, and meet the M14a targets on makako. Security semantics, outputs and retrieval quality stay unchanged: the M14 compare must report no hard failures and no quality changes.

**Out of scope:**
- semantic search (M15 onward);
- changing the authorization model;
- horizontal scaling or new backend services;
- caches of authorization decisions.

## 3. Decisions

| ID | Decision | Rationale |
|---|---|---|
| D1 | **Phase timing.** Extend the M14a metrics line with per-phase wall time (plan build, binding source, content fetch, finalize, render or apply stages) and per-backend cumulative time. `scripts/perf_probe.py` reports both. It is the first deliverable, and every later step is judged by it. | The makako gap is unexplained; the counters give counts, not time. |
| D2 | **Binding-source choice by measured cost.** `use_scan` picks the whole-store scan or parallel per-object reads by the *measured* tuple count (all kinds) and round-trip latency, not the journal binding estimate. The read concurrency becomes configurable (default 16, reference 32). Decisions are unchanged: both sources return the same tuples (M09a D4). | Scan pages are sequential and grow with the store: about 10 at S, about 30 at M, twice per read. |
| D3 | **Finalize freshness through the OpenFGA change log (OD1).** Build records the store's change-log continuation token. If the OpenFGA change log since that token contains no `bound_to` or `reader` change, and the journal head is unchanged, `finalize` reuses the build's inputs. Otherwise it repeats the full fresh reads. This is a verified invalidation strategy (AGENTS.md §5.3), reconciled by one fresh call. | Removes one ListObjects call and one whole-store scan per read, about half the remaining OpenFGA work. |
| D4 | **Lean journal listing (OD2).** Large payloads (operation records, idempotency responses, validation reports) move to a second document class. The security listing that every step reloads (`documents_at_version`) then holds only scopes, bindings, operation headers and ChangeSet headers. Reading a large payload is a direct get by ID. A one-time, journaled migration converts existing entries; it is idempotent and refuses to run while an operation is pending. | The listing is reloaded after every journal write and grows with history; it is the main fixed cost of small writes. |
| D5 | **Scheduled maintenance.** `c1-admin maintenance optimize` is documented as a periodic task (a systemd timer example and a frequency) for the knowledge, workflow and `_system` databases. The measured effect is recorded. | Delta-layer growth slows every journal read (M07 and M13 evidence). |
| D6 | **Reference resource limits (OD3).** Measure the S benchmark with the current compose caps (OpenFGA 1 CPU, TerminusDB 1.5, C1 2, PostgreSQL 1) and with raised caps on the same host. Document the sizing guidance; change the reference defaults only if the gain is material. | Separates CPU contention from code cost. |
| D7 | **History index (OD4).** `/v1/history` is served from the journal: applied `changeset_apply` operations record their targets, the ChangeSet ID is recorded in the commit message, and the commit ID comes from the receipt. The result is checked against TerminusDB history for equivalence in tests. TerminusDB history remains the fallback for untracked resources (written before journaling). | About 7 s of TerminusDB history scan per request today. |
| D8 | **Smaller items.** Remove repeated journal head reads within one authorization step, keeping the before/after comparison. Build each context path step's adjacency once (M14a C2). Compute the `_project_records` visibility set once (M14a B4). Also measure the 1 s keep-alive expiry (an M09a owner decision; it is changed only with owner approval). | Small fixed costs that matter only once the larger ones are gone. |

## 4. Owner decisions

| ID | Question | Recommendation |
|---|---|---|
| OD1 | May `finalize` rely on the OpenFGA change log since build, instead of repeating ListObjects and the scan, while repeating them whenever any relevant change exists? | **Yes**, with an ADR and tests: injected grant revocation, binding change and membership change between build and finalize must each force the full fresh path. |
| OD2 | Approve a journal storage change (a second document class) with a one-time migration? | **Yes**, behind the migration plan and a backup-and-restore test (M13 T03/T04 must still pass). |
| OD3 | May the reference compose defaults change if the measurement shows material gains? | Decide after the D6 measurement. |
| OD4 | Serve history from a journal-derived index, falling back to TerminusDB history? | **Yes**, if D1 confirms history as a priority. Otherwise defer. |

**Owner decisions recorded (2026-10-06):**

- OD3 is approved: the reference defaults may change if the D6 measurement shows a material gain.

## 7. Risks

- **D3 freshness.** This is the security-sensitive change. If the change-log semantics of the pinned OpenFGA 1.21.0 (horizon offset, consistency) can't be shown to be immediate, D3 is dropped and finalize keeps the full fresh reads.
- **D4** changes stored journal data. The migration must be reversible from the M13 backup, and its evidence includes a restore round trip.
- **Fixed costs on a shared host.** Some makako cost may be host contention that only D6 sizing addresses. That is reported, not hidden.
