## 2. Goal and boundaries

**Observable result.** `uv run --locked python -m benchmark run` bootstraps a fresh reference deployment, loads a declared synthetic corpus through the public API, executes a declared query and context set as declared principals, and writes `results.json` with five separate score families:
- storage fidelity;
- retrieval quality;
- security invariance;
- context quality under budgets;
- performance.

A committed baseline (`benchmark/baselines/v1-makako.json`) and a `compare` command classify any later change per family. **No aggregate score exists.** Fidelity and security failures are hard failures regardless of other numbers.

**In scope.**
- A seeded corpus generator with gold labels written from the corpus construction, never from C1 outputs.
- Metric implementations and runners for T01–T05.
- The twin-corpus and revocation procedures.
- An ablation registry (T06), whose only available configuration is the deterministic baseline.
- Baseline and compare; evidence; the report.

**Out of scope.**
- Semantic or vector retrieval and decision gates (M15–M18).
- Ranking changes or optimization of C1.
- Any change to retrieval semantics.
- External corpora or real company data.
- Publishing results.

## 3. Decisions

| ID | Decision | Rationale |
|---|---|---|
| D1 | **Harness location.** A new top-level package `benchmark/` (`corpus.py`, `gold.py`, `metrics.py`, `runner.py`, `families/*.py`, `__main__.py`), and `benchmark/baselines/`. It uses `tests/integration/m13/reference.py` for deployment and identities, and the public API only. | Reuses the M13 reference path (TLS, production Keycloak, internal network), so the measurements describe the candidate as deployed. No backend access, which AGENTS.md §4.2 and §9 require. |
| D2 | **Corpus `bench-v1`** (deterministic, `seed=14`, `uuid5` IDs under `urn:c1:instance:dev:`, scale factor `s`). Per unit of scale: 4 companies; 8 products per company with 3 versions; 1 battery per version, with measurements `capacity` and `cycle_life`, some conflicting with distinct sources; 24 people with 1–2 employments carrying `validDuring` intervals (known, year-only and unknown bounds); keywords and aliases on a declared subset; 6 documents with 6 ordered parts each across 3 scopes; sources, evidence and activities for imported claims. Profiles: `directory`, `topics`, `batteries`. Scopes: `bench-public`, `bench-team`, `bench-legal` and `bench-hidden`. Scales: **S (`s=1`)** and **M (`s=3`)**, both below the 5,000-candidate ceiling for the tested principal (checked at generation). | Covers PLAN.md T01's record kinds. The typed-path structure (company → product → version → battery) gives graph queries whose relevant items lack the anchor's keyword (the A15 pattern), so keyword and graph strategies differ measurably. |
| D3 | **Gold labels.** Every query is an *information need* with a gold set computed from the generator's own structures. Examples: "batteries of company X" is the batteries reachable through the typed path, restricted to what the tested principal may read; "employees of X valid at T" comes from the generated intervals. Gold is written to `gold.json` with the corpus manifest, before any query runs. Context needs carry `required_units`: the node and predicate pairs whose evidence must appear. | PLAN.md requires independent gold mappings. Generator-derived gold never depends on C1 behavior. |
| D4 | **Query set (about 60 per scale).** Families:<br>• keyword ANY/ALL (exact; sanity, expected recall 1);<br>• alias exact; label prefix;<br>• typed filter plus `valid_at`;<br>• **graph needs**, run with three strategies: keyword-only, neighborhood traversal (depth ≤ 3, declared predicates) and `graph-context`;<br>• document `text_contains`;<br>• context needs at budgets 8 KiB, 32 KiB and 64 KiB.<br>Each query declares K ∈ {5, 10, 50}. | Covers PLAN.md T02's metric families. Strategies are the existing deterministic surfaces; nothing new is invented. |
| D5 | **Metrics.** Binary relevance, per query, then the macro-average per family and strategy: Recall@K, Precision@K, nDCG@K (log2 discount), MRR, **path recall** (the share of gold typed paths present in `graph-context` orientation paths), **context coverage** (the share of required units present on the first page within the budget, plus the pages needed to reach full coverage through continuation). Ranks are C1's deterministic order; nothing is re-ranked. | Standard IR metrics. C1's order is not relevance-ranked, and the baseline records that honestly. |
| D6 | **Storage fidelity (T01).** Each generated record is read back through `/v1/resources/{id}` as an all-scope reader and compared field by field with the submitted record after canonicalization (IRIs, typed and language-tagged literals, multiplicity). Also checked: conflicts keep both claims with their sources; intervals keep precision and unknown bounds; documents return parts in `(order_key, id)` order with matching text digests; the export page round-trips through `import_jsonld` with identical identities. Score = exact records / total. **Any loss fails.** | PLAN.md T01; AGENTS.md §4.1. |
| D7 | **Security invariance (T03).** Every query and context need runs as the tested principal; observations are canonicalized (removing only revision tokens, cursors and timestamps). Then, in the same repository, the harness adds `bench-hidden` resources designed to be highly relevant: entities with the same keywords and label prefixes; relations into visible companies; measurements on visible batteries; document parts containing the queried text. The full run repeats, then again after modifying those hidden resources through ChangeSets. **Every observation must be byte-identical:** result sets, order, counts, pagination, explanations, paths and context Markdown and structure. Score = identical observations / observations; anything below 1.0 fails. | PLAN.md T03; the M05-T03 and M08-T07 methods applied at benchmark scale. |
| D8 | **Revocation (T04).** Revoke the tested principal's `bench-team` reader role and rerun all queries at head **and at the pre-revocation revision**. No team resource may appear in either. Re-grant and confirm the baseline observations return. | PLAN.md T04; AGENTS.md §5.2. |
| D9 | **Performance (T05).** Per scale:<br>• corpus load time;<br>• median and p90 over 5 repeats per query family and strategy;<br>• context build time per budget;<br>• OpenFGA requests per query (from the OpenFGA log, as in M13);<br>• C1 memory peak (cgroup `memory.peak`);<br>• TerminusDB storage growth (`du` of the storage volume before and after loading).<br>The host is recorded as in M13. Results are described as measurements on makako only. | PLAN.md T05; architecture §15.2. |
| D10 | **Ablations (T06).** `benchmark/configurations.py` registers `deterministic` (available) and `semantic-seeds`, `semantic-plus-gate` and `hybrid-plus-gate-plus-graph` (each `available: false`, citing M15/M16). The runner executes every available configuration against the same gold data. Unavailable ones are reported as `NOT_AVAILABLE`, which is not a failure: the roadmap test applies "when optional components are available". | PLAN.md T06: no optional component is needed to run the baseline. |
| D11 | **Repeats, thresholds and compare.** Quality and fidelity are deterministic: one run. Performance: 5 repeats. `python -m benchmark compare --baseline … --results …` classifies:<br>• **hard failure:** fidelity < 1.0, security invariance < 1.0, or a revocation leak;<br>• **change:** any quality metric differing from the baseline, reported as an improvement or regression for review, never silently accepted;<br>• **performance warning:** median latency > 1.5× the baseline on the same host class.<br>The baseline file stores the corpus manifest digest, gold digest, C1 revision and host. | PLAN.md "regression thresholds" and "statistical repeat count". |
| D12 | **Evidence format.** Under `docs/evidence/M14/`: `corpus-manifest.json` (seed, scale, counts, digests), `gold.json`, `results-S.json`, `results-M.json`, `run.log` and exits. `benchmark/baselines/v1-makako.json` holds the baseline subset; `docs/benchmark/README.md` is the human description; the report is `docs/milestones/M14-report.md`. | PLAN.md "retained evidence format". |

## 7. Recovery and security

The benchmark writes only synthetic data into a disposable reference deployment that it tears down afterwards. Credentials come from the M13 test-identity mechanism and are never written to evidence. A failed run leaves no committed baseline change; the baseline is updated only by an explicit `--write-baseline` run recorded in the report.
