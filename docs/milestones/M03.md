## 2. Goal and boundaries

**Observable result.** A running C1 application process (no product CRUD) that authenticates bearer tokens from the pinned Keycloak, attributes human and service principals, evaluates every protected operation against the OpenFGA v1 model using current bindings and current grants, performs audited security operations (scope provisioning, membership, resource provisioning, re-scoping with declassification review, recovery) through a durable journal, and fails closed in readiness and in every check when identity, authorization, or binding state cannot be trusted. Seven roadmap tests pass against the real Keycloak, OpenFGA, and TerminusDB.

**In scope.** HTTP application skeleton with Problem Details errors; token validation; principal model; OpenFGA product model v1 and client; authorization plane API used by all later milestones; binding and security-operation journal; security administration endpoints; readiness; a probe route group that reads synthetic M02 records under authorization, enabled only by explicit configuration.

**Out of scope.** ChangeSets and knowledge writes (M04), queries and cursors (M05), documents (M06), browser sessions and PKCE login flow (M12), positive authorization caches (none in the MVP unless a later plan proves invalidation), any endpoint that lists or mutates knowledge.

**Invariants touched.** AGENTS.md §5.1 (trusted issuer plus subject; independent resources; scope creation rights; no grants from membership or domain edges), §5.2 (current bindings govern old content; re-scoping separately authorized and audited; no distributed transaction assumed; fail closed), §5.3 (authorization before matching; cursors are not tokens; no unproven positive caches).

| D1 | **HTTP application.** FastAPI 0.141.1 on uvicorn 0.54.0 in `src/c1/api/`. Errors use RFC 9457 Problem Details with types `about:blank#authentication`, `#authorization`, `#validation`, `#not-found`, `#unavailable`. Hidden and nonexistent resources both answer `404` with an identical body; authorization failures on operations the caller may know about (security administration) answer `403`. Configuration comes only from `C1_*` environment variables read at startup (`src/c1/config.py`): instance IRI base, trusted issuer URL and its alias, expected audience, OpenFGA URL/store/model/token, TerminusDB URL/credentials/database names, `C1_INDEPENDENT_REVIEW` (default `true`), `C1_ENABLE_PROBE_ROUTES` (default `false`). | D2 | **Identity validation.** PyJWT 2.15.0 with `PyJWKClient` against the realm JWKS. | D4 | **OpenFGA model v1** in `deployment/openfga/c1-v1.fga` (the M01 prototype file stays untouched): ``type user``; ``type group { member: [user] }``; ``type instance { schema_admin, access_admin, operator: [user, group#member] }``; ``type scope { reader, contributor, creator, reviewer, access_admin: [user, group#member] }``; ``type resource { bound_to: [scope]; inherits_from: [resource]; can_read: reader from bound_to; can_contribute: contributor from bound_to; can_review: reviewer from bound_to }``. ADR-0009. |
| D5 | **Binding semantics.** Every resource that exists in any knowledge revision has exactly one `bound_to` tuple and one `Binding` journal record in the workflow database `{resource_id, scope_id, state ∈ provisioning|active|transitioning|revoked|failed, inherited_from, operation_id}`. A read is allowed only if: journal state is `active`; OpenFGA reports exactly one `bound_to` tuple equal to the journal scope; the fresh check `user can_read resource` allows. Zero or multiple tuples, missing journal, any state other than `active`, or any transport error deny. Deleted resources keep their binding record (state `active` or `revoked`) as long as history contains them; `revoked` is the deny tombstone. Inheritance is materialized: provisioning a DocumentPart without an explicit scope copies the document's current scope and records `inherited_from`; re-scoping a document cascades to inheriting resources inside the same journaled operation. | M01-T05/T06 evidence for exactly-one binding and journal gating; spec F08 items 2, 4, 5. |
| D6 | **Authorization plane API** (`src/c1/authorization/plane.py`), the only entry point later milestones may use: `check_read(principal, resource_id)`, `check_operation(principal, op, resource_id)`, `check_scope(principal, op, scope_id)`, `check_instance(principal, op)`, `batch_read(principal, resource_ids)` (chunks of at most 50 via BatchCheck, then applies D5 per resource), `bindings(resource_id)`. Decisions carry a `reason` code for audit only, never returned to clients. No positive cache exists; `HIGHER_CONSISTENCY` is set on every call; OpenFGA client timeout 2 s. Enumeration of readable resources (`ListObjects`) is not part of M03; M05 decides bounded enumeration with the 1000-result default in mind. | Architecture §6.3–§6.4; AGENTS.md §5.3 "do not retain positive authorization caches without a verified strategy". |
| D7 | **Security operations and journal.** `SecurityOperation {id, kind ∈ scope_create|scope_retire|membership|instance_grant|provision|rescope|recover, actor, target, from, to, state ∈ proposed|approved|pending|applied|failed|abandoned, approvals[], steps[], created, updated}` in the workflow database. All operations run under the M01 publication lock (asyncio lock plus advisory file lock) in the single application process; reads never take the lock and deny while a `transitioning` binding or `pending` operation targets the resource. Authority: `scope_create` and `instance_grant` need `instance#access_admin`; `membership` needs `scope#access_admin` on that scope; `rescope` needs `scope#access_admin` on **both** source and destination scopes; when `C1_INDEPENDENT_REVIEW=true` a `rescope` also needs an `approve` by a **different** principal holding `scope#access_admin` on the destination before `apply`, because scopes have no total order and every move is treated as a potential declassification. `scope_retire` is refused while any `bound_to` tuple or `Binding` record references the scope. Recovery (`recover`) runs at startup and on demand: it completes or fails every non-terminal operation before readiness reports ready. | Spec §7 (security mutation is separate), F08 items 6 and 7; architecture §9.3–§9.4; M01-T06 protocol. ## 7. Recovery and security

| Failure point | Behavior |
|---|---|
| Keycloak protocol mappers behave differently on the pinned release | Record the exact token claims; adjust mapper configuration only; the validator's rules in D2 do not loosen. |
| OpenFGA rejects `.` in user object ids | Switch the principal encoding to `user:{alias}_{sub}` and record it in ADR-0009; identity semantics do not change. |
| BatchCheck unavailable or limited | Fall back to sequential Check with the same fail-closed rule; record latency. |
| Recovery cannot decide an operation | The operation stays non-terminal, affected resources stay denied, readiness stays 503, and the report records the blocker. |
| Two application processes started by mistake | The advisory file lock makes the second fail its first security operation; `make api-up` refuses to start a second instance. |

Secrets: realm user passwords and client secrets are generated into the ignored `deployment/.env` (mode 0600); tests read them from there; logs never print tokens. No positive authorization cache exists, so revocation needs no invalidation step. Already delivered responses are not recalled.

## 9. Execution revalidation

The M02 report and actual code at `7db3326` confirm canonical IDs, typed record
validation, immutable lexical storage, and non-authoritative historical scope
hints. The configured storage client did **not** yet support historical reads.
M03 adds the narrow M01-proven commit read and probe revision methods needed by
T04, plus the separate operational journal; it does not implement M04 CRUD.

[Implementation contracts](M03-interfaces.md) define the module handoffs and
security choices. D2's 30-second leeway means T01 must wait beyond that leeway
for a one-second token to expire. `nbf` is validated when present; Keycloak's
actual access tokens may omit it. Required signed claims remain issuer, audience,
subject, expiry, issued-at, Bearer purpose and human/service kind.

Reads remain free of the writer lock but check the current workflow revision
before and after content selection and reauthorize before returning data. All
security writers use lifetime process ownership plus coroutine serialization.
Cascade targets are frozen in the reviewed operation; a changed cascade or
binding makes apply stale. Recovery rechecks actor and approver authority.

Native OpenFGA model JSON is authoritative and its matching DSL is readable
documentation. The product uses HTTPX against the official native API, including
BatchCheck, without a custom policy interpreter; the existing SDK remains used
by unchanged M01 probes. Probe bodies are limited to 1 MiB and synthetic
`urn:c1:probe:` record identities; routes are disabled by default.

Completed revocations may be confirmed during recovery when their exact tuple
is already absent, even if self-revocation removed the initiating authority.
This only closes durable intent and introduces no grant. Pending probe revisions
still require an active, uniquely matching current binding and fresh contribution
authority. A lifetime file lock prevents a second local process from writing.

The implemented test filenames are mapped in the execution report. T06 uses
the same `scripts.api.up/down` lifecycle functions exposed by `make api-up` and
`make api-down`; the Make targets also receive a separate smoke check. The local
token demonstration uses HTTPX to avoid printing credentials or tokens.
