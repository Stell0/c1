## 2. Goal and boundaries

**Observable result.** An authenticated client creates a ChangeSet against a base revision, submits it, gets an exact-payload validation report, has it approved by an independent reviewer, and applies it. Apply rechecks the exact approved payload, the base revision, current bindings, and every target permission, then commits all knowledge operations in one backend commit whose message is the durable receipt, publishes new resources through the M03 provisioning protocol, and records provenance. Identical retries recover the same outcome; a reused key with different content fails; crashes before and after the commit reconcile without duplicates. Historical content and history listings are served under current bindings. Restores are ordinary compensating ChangeSets that leave current bindings untouched. Drafts, validation reports, and review decisions are visible only to authorized principals.

**In scope.** ChangeSet lifecycle and endpoints; operation kinds `create`, `replace`, `install_profile`; validation (structure, references, manual-statement rule, declared-conflict flags); independent review; apply with receipt and idempotency; crash recovery for apply; provenance activities; `GET /v1/resources/{id}` and `GET /v1/history`; restore metadata; workflow journal kinds for ChangeSets.

**Out of scope.** Query and filter endpoints, cursors, traversal, merge/split/undo (M05); documents and parts beyond generic record writes (M06); context (M07); executing incompatible migrations (refused with a migration proposal record; execution needs a separate owner decision); browser sessions (M12); multi-process writers (M13 limitation).

**Invariants touched.** AGENTS.md §4.3 (all ordinary writes through ChangeSets; mutation after validation invalidates; apply rechecks everything; cross-scope all-or-nothing; idempotency bound to principal, repository, digest; restore is a new change), §4.1 (conflicting claims preserved, manual claims attributed), §5.1–§5.3 (creation needs scope permission; drafts and review output authorized; hidden references not disclosed).

## 3. Decisions to resolve

| ID | Decision | Rationale, evidence, proof obligation |
|---|---|---|
| D1 | **ChangeSet states and transitions.** `draft → submitted → validated → approved → applied`; terminal `rejected`, `stale`, `failed`, `withdrawn`. Transitions: `submit` (author), `validate` (server, on submit or on demand), `approve` (reviewer), `reject` (reviewer), `apply` (reviewer or approver), `withdraw` (author, before apply), `rebase` (author; sets a new base revision and returns to `submitted`, requiring revalidation and re-approval), `edit` (author; replaces operations and returns to `draft`, clearing validation and approval). `stale` is set by `apply` when the base is no longer the head; `failed` when apply raised a non-retryable error after validation; both allow `rebase` or `edit` into a new attempt with a new `attempt` counter. All state lives in the workflow database as journal kind `ChangeSet`. | Spec §7; PLAN M04-T02 (mutation invalidates), M04-T05 (stale). |
| D2 | **Operations.** `create {record, scope_id, inherited_from?}`, `replace {resource_id, record, reason}`, `install_profile {profile}`. A ChangeSet holds either only `install_profile` operations or only content operations. `replace` supplies the full record (including `lifecycle: superseded|retracted` for retraction with `reason` mandatory); no physical deletion exists in ordinary ChangeSets, so one `PUT create=true` covers every content operation. Limits: 200 operations, 1 MiB body. The record `id` in `create` may be omitted (server mints a UUID under the instance base and reports it in the validation report and receipt) or supplied when it is a canonical IRI under the configured instance base and not yet bound. | Retraction as lifecycle change follows spec F03; single PUT gives one backend commit (proven). Minting on the server keeps identity independent of producers (ADR-0006). |
| D3 | **Request digest and idempotency.** `request_digest = sha256(canonical JSON of {base_revision, operations, rationale})` with sorted keys and no whitespace. `POST /v1/changesets` and `POST /v1/changesets/{id}/apply` require an `Idempotency-Key` header (1–128 printable ASCII). Journal kind `Idempotency` stores `(principal_id, repository, key) → {digest, changeset_id, response}`. Same key and digest → the stored response (status 200 with `replayed: true`); same key, different digest → 422 `idempotency_conflict`. The apply receipt written into the knowledge commit message is `{"c1":2,"changeset":<id>,"attempt":<n>,"principal":<p.id>,"repository":<db>,"digest":<approved_digest>}`; `approved_digest` is the digest of the exact approved payload. | Spec §7 idempotency; ADR-0005 receipt format v1 (`m01`) is extended, not replaced; M01 probes stay unchanged. |
| D4 | **Validation report** (journal kind `ValidationReport`, one per attempt): M02 diagnostics for every record; reference resolution against the base revision where an unreadable or nonexistent referenced resource yields the same `C1-CS-010 unresolved_reference`; the manual-statement rule (`C1-CS-011`: an assertion without `evidence_ids` must have `manual_statement=true` and `attributed_to`; `origin=imported|derived` requires evidence or an activity); declared-conflict flags (`C1-CS-020`, informational: same subject and predicate, different object, overlapping known valid intervals, predicate declared single-valued by the profile); permission preview per operation (`allowed`/`denied` reason codes only); minted identifiers. A report with any `error` diagnostic sets `rejected` with reason `validation`. | Spec F03, §7; PLAN M04-T01, T07. Codes `C1-CS-*` are new and listed in the report. |
| D5 | **Authority.** `create` → `check_scope(p, "create", scope_id)` for the author at validation and for the executor at apply; `replace` → `check_operation(p, "contribute", resource_id)` for the author and `check_operation(reviewer, "review", resource_id)` for approval and apply; `create` approval and apply → `check_scope(reviewer, "review", scope_id)`; `install_profile` → `check_instance(p, "schema_admin")` for author, approver, and executor. `approve` requires a principal different from the author when `C1_INDEPENDENT_REVIEW=true` (existing setting); `reject` needs the same review authority as `approve`; `apply` may be run by the approver or any principal holding review authority over every target. Denied targets produce a whole-ChangeSet 403 at validation preview time only for the author's own operations; at apply time any denial fails the whole apply with nothing written (M04-T03). | Spec §3.3, A08; ADR-0009 capability separation. |
| D6 | **Apply protocol** (extends M03 provisioning to many records under the same writer gate): (1) load the exact approved payload and recompute its digest; mismatch → `failed` with `payload_mismatch`; (2) recheck state `approved`, base revision equal to the current knowledge head (`stale` otherwise), current bindings of every `replace` target active and not pending, every permission in D5; (3) journal CAS: operation `changeset_apply` `pending`, `provisioning` bindings for every `create`, ChangeSet `applying`; from this point reads of all targets deny; (4) idempotency check by scanning the knowledge log for a receipt with this ChangeSet id and attempt (recovery path); if absent, one `PUT create=true` with all records plus one server-minted `ActivityRecord` per target scope (actor, method `changeset-apply`, `used` = evidence and source ids in that scope, `outputs` = created and replaced ids in that scope, `result_revision` filled on the receipt), message = receipt, `expected_head` = base revision; (5) `bound_to` tuples for every created record and activity (one OpenFGA `Write` per ≤100 tuples); (6) confirm tuples and content at the new commit; (7) journal CAS: bindings `active`, `ApplyReceipt`, ChangeSet `applied`, operation `applied`. Crash points `journal`, `commit`, `tuple`, `confirm` (enabled only with probe routes). Recovery reuses step 4's log scan so a commit that lost its acknowledgement is never repeated. | ADR-0005 receipt, ADR-0010 protocol; PLAN M04-T01, T03, T04. Proof: `/api/log` paging (`count`/`start`) in the product client is verified by M04-T04 with more than one page of commits. |
| D7 | **Knowledge head versus workflow.** Only apply and profile installation write to the knowledge database. Every other ChangeSet action writes to the workflow database. `stale` is decided by comparing the ChangeSet base with the knowledge head, never with the workflow head. | Architecture §4.4; PLAN M04-T05. |
| D8 | **Schema-bearing ChangeSets.** `install_profile` for a registered additive profile runs `install_additive_profile` inside apply: precondition checks (registered, compatible, not installed) → schema commit → marker commit. Between the two commits the existing guard makes every knowledge read and write fail closed for this database; readiness reports 503; recovery completes the marker commit on restart. A profile whose comparison yields `C1-PR-004` is refused at validation and a `MigrationProposal` journal record is created naming affected classes and required checks; no schema or data is written. Data that depends on the new classes is submitted in a following content ChangeSet whose base is the head after installation. | M02 install functions and guard; spec F07 "dependent schema and data changes become visible together, or the migration is rejected before publication" is met by the guard: data referencing the new classes cannot exist before the marker, and schema without marker is invisible to the product. PLAN M04-T07. |
| D9 | **Visibility of drafts and review output.** `GET /v1/changesets/{id}`, its validation report, and review decisions are readable by the author and by principals holding review authority over every target (D5). Everyone else receives the identical 404. `GET /v1/changesets` lists only the caller's own ChangeSets plus those the caller may review, with target identifiers included only when readable. Reviewers see the full payload only when `check_read` allows every target and every referenced resource; otherwise 404. | Spec §3.3, F08 noninterference; PLAN M04-T06. |
| D10 | **History and historical reads.** `GET /v1/resources/{id}?revision=` returns the record at head or at a knowledge commit after the M03 read gate (this generalizes the probe read; probe routes remain unchanged). `GET /v1/history?resource_id=&limit=&cursor=` returns, newest first, `{revision, recorded_at, changeset_id, attempt}` for commits in which the resource changed, using `/api/history` and the receipts in commit messages; principal identifiers are returned only as the opaque principal id already visible in the ChangeSet when the caller may read that ChangeSet, otherwise omitted. Authorization: current binding of the resource; cursor = opaque base64 of `(revision, offset)` reauthorized on every page. | Architecture §8.3; PLAN M04 "historical content inspection"; ADR-0009 current bindings on history. |
| D11 | **Restore.** A restore is a ChangeSet of `replace` operations whose records come from `GET /v1/resources/{id}?revision=old`; the client sets `restores_from_revision` on the ChangeSet, the server verifies each restored record equals the content at that revision (else `C1-CS-030`) and records the lineage. Bindings, grants, and journal are not touched by a restore. | Spec §7 "restores are reviewed compensating knowledge changes"; PLAN M04-T06. |
| D12 | **Layout.** `src/c1/changes/` (`models.py` state machine and payload types, `digest.py`, `validation.py`, `apply.py`, `history.py`, `idempotency.py`), `src/c1/api/routes/changesets.py`, `routes/resources.py`, `routes/history.py`; `Journal._KINDS` gains `ChangeSet`, `ValidationReport`, `ReviewDecision`, `ApplyReceipt`, `Idempotency`, `MigrationProposal`; `Terminus` gains `history(document_id)`, `log(start, count)`, and a `message` parameter on `_put`/`_insert` callers (`write_records`, `replace_records`, new `upsert_records`). The M02 workflow record models (`ChangeSetRecord`, `ValidationReport`, `ReviewDecision`, `ApplyReceipt`) are the payload shapes stored in the journal and the export representation; they are not written to the knowledge database. No new dependency. | Architecture §3 module table and §17 (`changes/`). |
| D13 | **Endpoints.** `POST /v1/changesets`, `GET /v1/changesets`, `GET /v1/changesets/{id}`, `PUT /v1/changesets/{id}/operations` (edit), `POST /v1/changesets/{id}/submit|validate|approve|reject|apply|withdraw|rebase`, `GET /v1/changesets/{id}/validation`, `GET /v1/resources/{id}`, `GET /v1/history`. All bearer-authenticated, strict bodies, Problem Details. No convenience write route exists. | Architecture §7. |

## 7. Recovery and security

| Failure point | Behavior |
|---|---|
| `/api/log` paging parameters behave differently on the pinned server | Record the exact behavior; if unpaged, bound the scan by the ChangeSet's `created` time and record the limit in ADR-0011; never skip the receipt check. |
| Knowledge commit succeeds but the process dies before the journal update | Recovery scans the log for the receipt, then continues from step 5 (D6). |
| OpenFGA write fails after the commit | Bindings stay `provisioning`, targets stay denied, readiness 503, operator retry through `POST /v1/security-operations/recover`. |
| Additive schema commit succeeds, marker fails | Guard fails closed for the database; recovery writes the marker; no data referencing new classes can exist. |
| Idempotency record lost after a commit | The log receipt is authoritative; the record is rebuilt from it. |

Secrets: none new. Rollback: `git revert`; test databases are per-test. No positive caches. Already delivered bytes are not recalled.
