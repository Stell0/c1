## 2. Goal and boundaries

**Observable result.** A versioned, published knowledge profile (`profiles/core/`: JSON-LD context, vocabulary description, SHACL shapes, TerminusDB schema, manifest) and a Python model layer (`src/c1/model`, `src/c1/interchange`, `src/c1/storage`) such that a JSON-LD fixture in the supported profile can be validated, mapped to backend records in the real pinned TerminusDB, read back, and exported to JSON-LD that is RDF-isomorphic to the normalized input. Unsupported constructs produce stable diagnostics and persist nothing. Keyword normalization and temporal semantics are pure functions with predetermined test vectors. A domain extension is added as data without changing core code.

**In scope.** Record types for Entity, Assertion (including relationship assertions), Source, Evidence, ProvenanceActivity, EntityResolutionRecord, Document, DocumentPart, SchemaProfile, and the *structure* of ChangeSet, ValidationReport, ReviewDecision, and ApplyReceipt. The storage mapping for the knowledge database. The first version of the `core-knowledge` fixture. A product storage client for TerminusDB derived from the M01 probe.

**Out of scope.** HTTP API, authentication, authorization checks, ChangeSet lifecycle and apply, queries over the graph, document reconstruction, the software profile, and any migration execution. M02 never exposes a network endpoint. No client-facing backend query escape hatch exists: the storage client is internal and constructs every request itself.

**Invariants touched.** AGENTS.md §4.1 (identity independent of producer/project/policy; assertions separate from entities; time dimensions distinct; aliases explicit), §6.1 (exact keywords, versioned normalization), §8 (standards profile, bundled contexts, explicit rejection, custom-term reasons).

## 3. Decisions to resolve

| ID | Decision | Rationale, evidence, proof obligation |
|---|---|---|
| D1 | **Namespaces and identifiers.** Vocabulary namespace `urn:c1:ns:core#` (prefix `c1`), extension profiles under `urn:c1:ns:<profile>#`. The instance namespace is deployment configuration `C1_INSTANCE_IRI_BASE` (development default `urn:c1:instance:dev:`); a canonical IRI is `{instance_base}{kind}/{uuid}` with kinds `entity`, `assertion`, `source`, `evidence`, `activity`, `resolution`, `document`, `part`, `changeset`. Identifiers are UUIDv4 from the standard library. Storage document IDs are `Entity/{uuid}`, `Assertion/{uuid}`, … under TerminusDB's default `@base`; the storage module maps between the two and storage IRIs never leave it. | Owner chose the URN namespace. UUIDv4 needs no dependency and leaks no creation time. Mapping in the storage layer, rather than setting `@base` to the instance IRI, keeps identity independent of backend layout by construction (AGENTS.md §4.1). Recorded in ADR-0006. |
| D2 | **Record layer** with pydantic 2.13.5 in `src/c1/model/records.py`. `EntityRecord` (id, types, labels as literal set, description, aliases, keywords, lifecycle); `AssertionRecord` (id, subject IRI, predicate IRI, object = IRI or `LiteralValue`, qualifiers: valid interval, origin, review state, lifecycle, optional attributed confidence, evidence IDs, activity ID, manual-statement flag with attribution, optional `provisioned_scope_hint`); `SourceRecord` (title, kind, locator, immutable revision or digest, publication metadata); `EvidenceRecord` (assertion ID, source ID, source version, selector, excerpt); `ActivityRecord` (actor principal, tool and version, method, inputs, outputs, started/ended); `ResolutionRecord` (candidates, decision, actor, rationale); `DocumentRecord` and `DocumentPartRecord` (structure only; ordering key type `order_key: str` chosen finally in M06); `SchemaProfileRecord`; workflow records `ChangeSetRecord`, `ValidationReport`, `ReviewDecision`, `ApplyReceipt` (fields from spec §4.5; state machine deferred to M04). `provisioned_scope_hint` is documented as historical provenance only; no code path in any milestone may read it for authorization, and M03 adds a test for that. | Spec §4; architecture §4.1. Validation of structure happens here and in SHACL; the two must agree and M02-T02 checks both. |
| D3 | **Literal representation.** `LiteralValue{lexical: str, datatype: IRI, language: str | None}`; `language` implies datatype `rdf:langString`. Supported datatypes: `xsd:string`, `rdf:langString`, `xsd:boolean`, `xsd:integer`, `xsd:decimal`, `xsd:double`, `xsd:anyURI`, `xsd:date`, `xsd:dateTime`, `xsd:dateTimeStamp`, `xsd:gYear`, `xsd:gYearMonth`. Lexical form is authoritative and validated against the datatype's lexical grammar; the storage mapping additionally writes typed shadow fields (`value_integer`, `value_decimal`, `value_boolean`, `value_double`, `value_earliest`, `value_latest` as `xsd:dateTime`) for the datatypes M05 filters on. Language tags must be well-formed BCP 47 and are lowercased on import (RDF 1.1 value space). Other datatypes are rejected with diagnostic `C1-IX-020`. | M01-T07 proved lexical/datatype/language fields round-trip. Shadows avoid depending on backend decimal or date semantics for exactness. Proof: M02-T01 exercises every supported datatype through the real backend. |
| D4 | **Supported JSON-LD input.** Accepted: `@context` equal to a bundled context identifier (`urn:c1:ns:core:context:1` or a registered profile context), `@id`, `@type`, `@value`, `@language`, `@graph`, `@set` containers, term definitions from bundled contexts, absolute IRIs and prefixed names from those contexts. Rejected before expansion with a diagnostic: inline context objects, non-bundled context IRIs, `@import`, `@included`, `@nest`, `@reverse`, `@list`, `@index`, `@json`. After expansion with rdflib, the triple graph is checked: no blank nodes (`C1-IX-010`), every predicate declared by the active profiles (`C1-IX-011`), every subject typed with a declared class (`C1-IX-012`), every literal within D3. Nothing is persisted if any diagnostic has severity `error`. | Architecture §5: bundle and pin contexts, reject or normalize deterministically. The M01 loader pattern (resolve bundled contexts before parsing) is reused. `@list` is rejected because RDF lists are blank-node chains and DocumentPart ordering uses an explicit order property. |
| D5 | **SHACL subset** in `profiles/core/shapes.ttl`: `sh:NodeShape` with `sh:targetClass`; `sh:property` with a single-predicate `sh:path`, `sh:minCount`, `sh:maxCount`, `sh:datatype`, `sh:nodeKind`, `sh:class`, `sh:in`, `sh:pattern`, `sh:languageIn`, `sh:hasValue`, `sh:or` (only to express "IRI or literal" objects). pyshacl runs with `inference="none"`; shapes in the data graph are ignored. Shapes constrain record structure only. Because each assertion is its own resource with exactly one object, two contradictory assertions and two legitimate `worksFor` assertions both validate. A shapes file using constructs outside this subset is rejected at profile load (`C1-PR-003`). | Spec F07; PLAN M02-T02. |
| D6 | **Keyword normalization `c1-kw-1`.** `normalize(s) = collapse_ws(strip(NFKC(casefold(NFKC(s)))))` where `collapse_ws` replaces every run of Unicode whitespace with one U+0020. Diacritics are kept (removing them would be a form of stemming). A keyword record stores `text` (original), `language` (optional, lowercased BCP 47), `normalized`, `normalization_version = "c1-kw-1"`. Coalescing key per entity is `(language, normalized)`; the first original spelling is kept and later duplicates are dropped with an informational diagnostic. Matching functions `match_any(entity_keywords, query)` and `match_all(...)` compare normalized values of the same language, or of any language when the query carries no tag; an empty query list adds no condition and returns `True`. No stemming, translation, or synonym expansion exists anywhere in the module. | Spec F02; PLAN M02-T05. NFKC before and after casefold follows Unicode's NFKC_Casefold guidance because casefolding can produce unnormalized output. |
| D7 | **Temporal semantics.** `TimeBoundary = Known(lexical, datatype ∈ {xsd:dateTimeStamp, xsd:dateTime, xsd:date, xsd:gYearMonth, xsd:gYear}) | Unknown | Unbounded`. `TimeInterval{start: TimeBoundary, end: TimeBoundary}` is half-open (start included, end excluded). Each known boundary gets derived comparable bounds by precision: `2020` → earliest `2020-01-01T00:00:00Z`, latest `2021-01-01T00:00:00Z`; `2020-05` → month span; `2020-05-03` → day span; `xsd:dateTime` without timezone keeps its lexical form, computes bounds as if UTC, and sets `timezone_unknown = true`, which M05 treats as indeterminate for strict queries. `Unknown` produces no bounds; `Unbounded` produces −∞/+∞ sentinels. Recording time is never a client field; it comes from the backend commit. No function fabricates a timestamp from a coarser value; only intervals are derived. Interchange uses OWL-Time (`time:hasBeginning`, `time:hasEnd`, `time:inXSDDate`, `time:inXSDgYear`, `time:inXSDgYearMonth`, `time:inXSDDateTimeStamp`) plus custom `c1:boundaryState` on each boundary with values `known`, `unknown`, `unbounded`, because OWL-Time cannot distinguish an unknown boundary from an unbounded one. | Spec F04; PLAN M02-T06. |
| D8 | **Custom vocabulary** limited to documented gaps; each term in `profiles/core/vocabulary.md` has a definition and a reason for not reusing an existing term. Reused: `rdf:Statement` (Assertion is a subclass), `rdf:subject/predicate/object`, `rdfs:label`, `skos:altLabel` (aliases), `skos:prefLabel` (labels), `dcterms:title/identifier/issued/creator/description`, `prov:Activity/Agent/wasGeneratedBy/wasAttributedTo/used/startedAtTime/endedAtTime`, `oa:hasSource/hasSelector/TextQuoteSelector/TextPositionSelector/exact/start/end`, `time:*` as in D7. Custom: `c1:Entity`, `c1:Assertion`, `c1:Source`, `c1:Evidence`, `c1:Document`, `c1:DocumentPart`, `c1:ResolutionRecord`, `c1:SchemaProfile`, `c1:keyword`, `c1:keywordText`, `c1:keywordLanguage`, `c1:normalizedKeyword`, `c1:normalizationVersion`, `c1:origin`, `c1:reviewState`, `c1:lifecycle`, `c1:confidence`, `c1:confidenceMethod`, `c1:manualStatement`, `c1:validDuring`, `c1:boundaryState`, `c1:sourceKind`, `c1:sourceRevision`, `c1:contentDigest`, `c1:excerpt`, `c1:orderKey`, `c1:partOfDocument`, `c1:provisionedScopeHint`. | AGENTS.md §8 requires the reason for each custom term. |
| D9 | **Storage schema.** One TerminusDB class per record type plus subdocument classes `LiteralValue`, `Keyword`, `TimeBoundary`, `TimeInterval`, `Selector`. Entities and assertions use explicit `@id` with `Random` keys; subdocuments use `ValueHash`. Multi-valued fields are `Set`; optional fields `Optional`. Storage uses only `xsd:string`, `xsd:integer`, `xsd:decimal`, `xsd:double`, `xsd:boolean`, `xsd:dateTime` (shadows), and `Enum` for `origin`, `reviewState`, `lifecycle`, `boundaryState`. The schema is installed on an **empty** knowledge database with `POST /api/document?graph_type=schema&full_replace=true` and an explicit `@context` that keeps the default `@base`/`@schema` and declares prefixes `c1`, `xsd`, `rdf`; the same call carries `@documentation` with the profile name and version. A `SchemaProfile` instance document records the installed profile version. | M01 showed `POST` without full replace rejects a context; the upstream test proves `full_replace` with `@context`. Proof: M02-T01 setup on the real stack, plus a negative check that installing over a non-empty database is refused by C1 (`C1-ST-001`). |
| D10 | **Schema versioning and compatibility.** `profiles/<name>/profile.json` declares `name`, `version` (semver), `requires_core`, `context`, `shapes`, `classes`, `predicates` (with ranges and cardinalities). `compare_profiles(old, new)` classifies each difference: **additive** (new class, new optional predicate, widened enum, new profile) or **incompatible** (removed or retyped predicate, narrowed cardinality, removed enum value, changed key strategy). Incompatible differences produce `MigrationRequired` diagnostics that name the affected classes and the data check needed; executing a migration is M04. The manifest version is stored in the `SchemaProfile` document so a running database knows what it has. | Spec F07 "explicit and versioned"; PLAN M02-T07. |
| D11 | **Extension points as data.** `ProfileRegistry` loads every `profile.json` from `profiles/` and from directories passed explicitly by tests. A profile contributes context terms, shapes, classes, and predicates; it cannot contribute code, validators, or hooks. The `software` profile name is reserved for M08 and no file is created now. | AGENTS.md §7 and §8: data-only profiles, no plugin system. |
| D12 | **Code layout and dependencies.** `src/c1/model/` (`ids.py`, `records.py`, `literals.py`, `keywords.py`, `time.py`, `diagnostics.py`, `profiles.py`), `src/c1/interchange/` (`jsonld.py`, `shacl.py`, `export.py`), `src/c1/storage/` (`terminus.py` product client derived from `probes/terminus.py` with a non-probe database guard and identical request construction, `schema.py`, `mapping.py`). Runtime dependencies added to `pyproject.toml`: `pydantic==2.13.5`, `rdflib==7.6.0`, `pyshacl==0.40.1`, `httpx==0.28.1`. Diagnostics carry `code`, `severity`, `path`, `message` with the code families `C1-IX-` (interchange), `C1-PR-` (profile), `C1-ST-` (storage). | Architecture §17 module names. Diagnostic codes give tests stable identities. |
| D13 | **Fixture `fixtures/core-knowledge/` v1** as JSON-LD plus expected outputs: entities Company Tesla (synthetic), Person Ada Example, Product Battery Pack v1; labels in `en` and `de`; aliases; keywords with and without language tags including case, whitespace, and NFKC variants; two contradictory revenue assertions from two sources with evidence excerpts; two `worksFor` assertions for one person; one attributed manual statement without a source; valid intervals with year-only, unknown end, and unbounded end; one PROV activity per import. `expected/` holds the canonical export, normalized keywords, and derived time bounds. | PLAN §4 fixture family; reused by M04–M07. |
| D14 | **Python version.** Stay on 3.13. `OPEN_CHOICES.md` item "Python 3.14 compatibility" is closed by this milestone: pyshacl 0.40.1 still declares 3.13 as its ceiling; revisit only when pyshacl publishes 3.14 support. | ADR-0001 amendment. |

## 7. Recovery and security

| Failure point | Behavior |
|---|---|
| `full_replace` schema install misbehaves (context rejected, or existing data not empty) | `C1-ST-001` refuses to install on a non-empty database; if the pinned server rejects the context form, record the exact response, mark T01 blocked, and propose a bounded alternative (per-class schema `POST` without context, prefixes expressed as full IRIs) for owner approval. |
| A supported datatype misbehaves in the backend | Remove it from D3's list only with an explicit owner-approved scope note in the report; lexical storage remains authoritative regardless. |
| pyshacl or rdflib behavior differs from expectation | Record the difference in ADR-0007; never widen the accepted subset to pass a test. |
| Fixture drift | Expected outputs are regenerated only by an explicit command and reviewed in the diff. |

Rollback is `git revert`; integration databases are per-test and dropped in teardown. No credentials beyond the existing ignored `deployment/.env`. The storage client refuses database names from callers and logs no request bodies.
