**Gaps this plan must close.**
1. There is no documentation that a documentation-only principal can read: all repository documents live in repository scopes. This plan adds published support guides in `sw-shared`.
2. Applicability is only the positive `describesSnapshot` declaration, and there is no way to declare a document explicitly not applicable to a target. M10-T01 needs that, while §10.5 leaves the full state enumeration to M11.
3. There is no structured notion of a support aspect (retry, timeout, configuration) that a request can name and a package can report as missing.
4. There is no two-request link that carries the first request's target and content snapshot into the second.

## 2. Goal and boundaries

**Observable result.** A consumer makes two explicit requests:
1. `support-documentation` for an anchor (a capability or operation), a target, and requested aspects. It returns, as one authorized package, the target-applicable support documentation (prerequisites, procedures, configuration, limitations), the applicable known warnings, and a `missing_aspects` list.
2. `support-implementation`, only if the consumer chooses, with a follow-up token from the first response and the aspects it still needs. It returns only the implementation, configuration, interface and test material that is readable by the caller, declared for those aspects, and pinned to the same target and C1 content revision.

Every unit carries an evidence-role label, and code evidence is never presented as an official procedure. No AI service, internal sufficiency judgment or autonomous fallback exists.

**In scope.**
- Two context profiles.
- Request fields for aspects and the follow-up.
- Applicability ordering and warnings.
- A minimal negative applicability declaration.
- Aspect vocabulary records and declarations.
- Fixture v1.2: guides, aspects and declarations.
- Twin and perturbation noninterference tests.
- Golden packages.

**Out of scope.**
- M11 applicability state enumerations, review candidates, part-level obsolescence rules, drafts and publication.
- Customer-facing publication modes. M10 packages are for the requesting principal only and are labelled accordingly.
- Free-text questions, ranking by text similarity, and synonyms or stemming of aspects.
- Explorer UI (M12).

**Invariants touched.**
- AGENTS.md §5.3: a profile grants nothing.
- AGENTS.md §6.2: missing does not mean nonexistent.
- AGENTS.md §7: documentation first, and the same target across both requests.
- §11.3: source-read rights are not publication rights.

## 3. Decisions to resolve

| ID | Decision | Rationale, evidence, proof obligation |
|---|---|---|
| D1 | **Profiles.** Two software-task profiles, `support-documentation` 1 and `support-implementation` 1, extend the M09 profile kind. The `software.task` enumeration gains these two values. Each has its own fixed section template: <br>• **Documentation:** interpretation, target, guidance, configuration, limitations, warnings, other-target documentation, missing aspects, sources, bounds.<br>• **Implementation:** interpretation, target, implementation, configuration, interfaces, observed tests, interpretations, missing aspects, sources, bounds.<br>`requires_target` is true for both. `requires_goal` is false, and a `goal` field is rejected. `requires_aspects` is true for implementation and optional for documentation. Role maps cover every unit kind. There are no free-text or executable fields. | ADR-0018 extension mechanism; spec §11.2–11.3. Proved by T01–T04. |
| D2 | **Aspects are declared, exact vocabulary.** `software` profile 1.2.0 adds:<br>• the entity class `Aspect` (a label plus explicit keywords, in a declared scheme);<br>• the predicate `addressesAspect` (DocumentPart, CodeSymbol, TestCase or Configuration → Aspect).<br>Requests name aspects by ID or by an exact label or keyword, using the M05 normalization rule: no stemming, translation or synonyms. An unknown or hidden aspect is reported as `unresolved` with no detail. The basis of each `addressesAspect` claim comes from its origin: `declared` for imported guide front matter, `interpretive` for an attributed analyzer claim on code. | Spec §6.1 exact keywords; aspects must be declared, never inferred. Proved by T02 and T06. |
| D3 | **Minimal negative applicability.** The predicate `software#notApplicableTo` (Document or DocumentPart → SourceSnapshot) is an attributed, evidence-backed Assertion, and it does not define M11's states. A document with a readable `notApplicableTo` for any target snapshot is never placed in guidance; it appears in `warnings` with its attribution and evidence. M11 may add richer applicability records. If M11 does, it must map this predicate onto them or preserve it; M11's plan records which. | Needed for M10-T01's obsolete guide; §10.5 keeps enumeration names in M11. One predicate with no enumeration is the smallest step. |
| D4 | **Applicability ordering (documentation stage).** A readable support Document is a candidate when it documents the anchor or one of its operations (`documents`) or carries an aspect-relevant part. It is classified as one of:<br>(a) **applicable:** a readable `describesSnapshot` to a target snapshot, and no readable `notApplicableTo` to a target snapshot;<br>(b) **declared not applicable:** goes to `warnings`;<br>(c) **other target:** documents the anchor but describes only non-target snapshots. It goes to `other-target documentation` as metadata only (title, described snapshots, issued date) with no text, so it cannot replace applicable guidance.<br>Applicable documents are ordered by review state (`confirmed` before `reported` before `disputed`), then by `dcterms:issued` descending as a tiebreak only, then by ID. Their parts are ordered by order key. | Spec §11.2, "applicability before age" (M10-T01). Proved by T01 and T04. |
| D5 | **Missing aspects.** For each requested aspect, the package reports whether at least one returned unit `addressesAspect` that aspect. Every requested aspect with no returned unit is listed in `missing_aspects` with the fixed text "not addressed by the returned material". Nothing about other material or its existence is stated. | Spec §11.3 and AGENTS.md §6.2. Proved by T02 and T06. |
| D6 | **Follow-up token.** Every documentation-stage response includes `followup`: the resolved target members, the C1 revision, `missing_aspects`, and a signed token. The token is made by the M05 cursor codec with order key `support-followup`. It binds the principal, the revision, a digest of the target members and anchor, and the profile pair. An implementation request carries either `followup_token` plus `aspects`, or an explicit `target` plus `revision`. With a token, C1 decodes it, uses its revision and target exactly, and reauthorizes everything under current grants and bindings. A token used by another principal, or mixed with a conflicting `target` or `revision`, returns 400 `C1-CX-001`. The documentation stage never runs the implementation stage. | Spec §11.3, "same source target set and selected C1 snapshot … unless the caller explicitly refreshes". Proved by T03. |
| D7 | **Implementation-stage selection (focused).** For the requested aspects only, the stage returns readable records at target snapshots:<br>• CodeSymbols with readable `addressesAspect`, their definition parts at the target, and direct dependencies (the M09 D4 rule);<br>• Configurations among the target's members with `addressesAspect`;<br>• InterfaceOperations linked from the selected symbols;<br>• TestCases with `addressesAspect` or verifying selected operations, with M09 run labels.<br>Nothing outside the aspect set is returned, so there is no source dump. The section caps are those of the M09 profile. | Spec §11.3, "only the relevant permitted code/test/interface paths". Proved by T02. |
| D8 | **Labels and audience.** Unit roles are as follows. Guide parts are `normative` and displayed as "official guidance". Code and configuration are `structural`, displayed as "implementation evidence, not a supported procedure". Analyzer claims are `interpretive`, and runs are `observed`. Every package states "prepared for the requesting principal; read access is not publication permission". M10 adds no publication request field. | Spec §11.3, §13.4. Proved by T04. |
| D9 | **No privilege escalation or existence leak.** The implementation stage uses the same authorized selection as every other path. For a documentation-only principal (Alice), the implementation package lists the requested aspects as missing. That package is byte-identical, except for declared volatile fields, between two copies of the fixture template, one of which has extra `sw-ledger` code records that address the same aspects. | AGENTS.md §5.3; spec §11.3. Proved by T05. |
| D10 | **Fixture v1.2 (data only, so the existing SCIP JSON is unchanged).**<br>• **Guides:** published support guides in `fixtures/software-integration/guides/`, imported as Documents in `sw-shared` with `sourceKind` `support-guide`, `dcterms:issued`, and part sections. Each guide's front matter declares the described snapshots, `documents` targets and `addressesAspect` per section, and the indexer maps these into records. The guides are:<br>&nbsp;&nbsp;– "Ledger operations guide 1.0", issued 2026-01-05. It describes a1 and b1, and has sections on configuration (`ledger_url`), the invoice-creation procedure, and limitations (amounts must be positive).<br>&nbsp;&nbsp;– "Ledger operations guide 1.1", issued 2026-02-05. It describes a2 and b2, has configuration and procedure sections, and **no retry or timeout section**.<br>&nbsp;&nbsp;– "Shop integration troubleshooting", issued 2026-02-20 (the newest). It documents `createInvoice` and declares `notApplicableTo` b2. Its procedure no longer applies after b2's customer field rename.<br>• **Aspect entities:** `configuration`, `retry`, `timeout` and `invoice-creation`.<br>• **Analyzer claims:** the analyzer attributes `addressesAspect retry` to a2 `create_invoice` and to b2 `post_invoice`.<br>• **Configuration:** the configuration `default` addresses `configuration`.<br>• **Timeout:** nothing addresses `timeout`.<br>• **Expected results:** golden packages for Carol, Dave and Alice are specified independently in the tests. M08-T02's expected document set is updated for the guides; no other earlier assertion changes. | Spec A19; data-only extension (M09 precedent). Proved by T01–T06. |

## 7. Recovery and security

| Failure point | Expected safe behavior and recovery |
|---|---|
| Token expired, malformed, for another principal, or mixed with a conflicting target | 400 `C1-CX-001` or 409 restart; never a silent new target. |
| A target member becomes unreadable between stages | 404 or 409, as in M09 D1. No substitution. |
| Aspect hidden or unknown | `unresolved`, with no detail. |
| A guide part becomes hidden after rescope | It is excluded on both stages; earlier responses cannot be recalled. |
| Ingested guide text containing commands or links | Rendered inert (M06 escaping), never executed or fetched. |
