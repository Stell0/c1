## 2. Goal and boundaries

**Observable result.** `POST /v1/context` with profile `test-development`, an explicit target set, an anchor (a symbol, capability or interface operation) and an explicit goal (`conformance` or `characterization`) returns one authorized selection, rendered as Markdown and structured JSON. It contains:
- The applicable normative expectations: documentation and contract excerpts.
- The target definition's code, labeled complete unit or excerpt.
- Directly needed types and interfaces.
- Error and side-effect facts where stored.
- Existing test definitions and fixtures.
- Test runs, labeled by whether they match the target and whether they are mocked or live.
- Attributed execution instructions, shown as untrusted text.
- Recorded discrepancies.
- Gaps.

Each item is labeled with its evidence role (normative, structural, interpretive, observed). A deterministic external consumer uses the package to target a reviewed synthetic test. The test fails on the defective snapshot and passes on the fixed one, and the results are imported as TestRuns. C1 itself neither writes nor runs tests.

**In scope.**
- The `test-development` profile.
- Context grammar extensions: `target`, `goal`, software sections, and role labels.
- The software selection stage over the M08 lookup service.
- Preserving code completeness in context output.
- The additive `software-testing` profile.
- The fixture extension (a deliberate discrepancy, a fixed snapshot, execution-instruction documents).
- The consumer demonstration and external runner.
- Golden packages.

**Out of scope.**
- The support profiles (M10), the documentation-update profile and applicability states (M11), and the Explorer (M12).
- Generating tests or prose.
- Any sufficiency judgment or model.
- Executing ingested commands.

**Invariants touched.**
- AGENTS.md §6.2: the same selection feeds both formats; nothing is inferred; missing is not reported as nonexistent.
- AGENTS.md §7: normative and implementation stay separate; a definition is not a run; mocked is not live; targets are pinned.
- AGENTS.md §5.3: no hidden code reaches the package through dependency expansion or citations.

## 3. Decisions to resolve

| ID | Decision | Rationale, evidence, proof obligation |
|---|---|---|
| D1 | **Request extension.** `/v1/context` accepts two new optional fields. `target` is either `{target_set_id}` or an inline M08 target set of snapshots, contracts and configurations; it takes no branch names, because branches are resolved separately through `/v1/software/targets/resolve`. `goal` is `conformance` or `characterization`. Both are required when the profile declares `requires_target`/`requires_goal`, and rejected with 400 `C1-CX-001` for profiles that do not declare them, so M07 behavior is unchanged. `request_digest` covers `target` and `goal`. The continuation cursor pins the resolved target members together with the C1 revision. Every page re-resolves the target under current authorization, and a changed or unreadable member gives 409 `C1-CX-011` restart, never a silent substitution. | Spec §11.1; §10.2 target pinning; M07 D1 strict grammar and D8 continuation. Proved by M09-T01 and M09-T03. |
| D2 | **Profile grammar extension, data-only.** `ContextProfile` gains an optional `software` block with `task: "test-development"`, `requires_target`, `requires_goal`, `anchor_kinds` ⊆ {symbol, capability, operation}, `dependency_depth` (0–1), `max_dependencies` (≤ 20), `max_tests` (≤ 50), `max_runs` (≤ 100), a `role_map` from software predicates and occurrence roles to evidence roles, and `sections` taken from the fixed test-development template: interpretation, target, normative, implementation, interfaces, tests, runs, fixtures, instructions, discrepancies, gaps, bounds. Graph `paths` are unused when `software` is present, and the validator requires exactly one of the two modes. There are no free-text templates and no executable fields. The M07 fixed eight-section template stays mandatory for graph profiles. | M07 D2 (profiles as validated data); architecture §13 "profiles extend the generic builder". |
| D3 | **Additive profile `software-testing` 1.0.0.** Its vocabulary is `urn:c1:ns:software-testing#`, installed after `software`. It adds `executionInstructions` (Document to CodeRepository, declared by repository documentation), `fixtureOf` (CodeSymbol to TestCase, declared in test code metadata or by attributed review), and `discrepancy` (an Assertion whose subject is the implementation part and whose object is the normative part, attributed and evidence-backed, origin manual or imported, with an optional `discrepancyNote`). A separate name avoids the same-name upgrade defect (M08 Conflict 2). | A18 "include a deliberate implementation/contract discrepancy and preserve it"; C1 never infers discrepancies. |
| D4 | **Software selection stage** (`src/c1/context/software.py`). It runs after anchor resolution and before units, and uses only the M08 lookup service and generic authorized reads. **(1) Target definition:** the anchor symbol's definition occurrence in the target snapshot, then its enclosing part. A capability or operation anchor expands to the symbols linked by `implementsCapability`/`implementsOperation` whose occurrences are in the target. **(2) Interfaces and types:** readable InterfaceOperations linked by `implementsOperation`/`declaredCall` from the target symbol, plus, when `dependency_depth` is 1, the definition parts of symbols with *reference* occurrences inside the target definition's range in the same snapshot, capped at `max_dependencies`, ordered by first occurrence and then symbol key. **(3) Normative:** readable Documents or parts linked by `documents` to the anchor, symbol or operation that also carry `describesSnapshot` for a target snapshot, plus the contract operation's part in the target contract version. **(4) Tests:** TestCases that `verify` the anchor or its operations, or whose `definedAt` occurrence in a target snapshot references the target symbol, with their definition parts. **(5) Runs** for those TestCases (D6). **(6) Fixtures:** readable `fixtureOf` symbols' definition parts in the target snapshot. **(7) Instructions:** readable `executionInstructions` document parts for the target repositories. **(8) Discrepancies:** readable `discrepancy` assertions whose subject or object is a selected part. Every step is bounded, deterministic, and computed over readable records only. | Spec §11.1 content list; M08 D3–D8 records. Proved by M09-T01. |
| D5 | **Evidence roles and goal labelling.** Each unit carries `role`, taken from the profile `role_map`. Normative covers documents, contract parts and `verifies` intent. Structural covers code parts, occurrences, `staticCall`, `declaredCall` and `implementsOperation`. Interpretive covers `interpretedCall`, `implementsCapability` and `discrepancy` with origin manual. Observed covers TestRuns and `exercised`. Normative and implementation text are never merged into one unit. With `goal: conformance`, the header states that the normative section is the only oracle source and that implementation shows current behavior. With `goal: characterization`, the header states that implementation behavior is being characterized and that normative expectations are shown for comparison. The goal changes labels and section headers only, never the selection. | Spec §10.4, §11.1 ("characterization and conformance are distinct declared goals"). Proved by M09-T02. |
| D6 | **Run matching.** A TestRun is `matching` only when its snapshot set, restricted to the repositories in the target, equals the target's snapshots for those repositories, and its configuration equals a target configuration, or both are absent. Otherwise it is `other-target` and shows its own snapshots and configuration. `integrationMode: mocked` runs are labeled mocked and list the mocked products. A run is `integration evidence` for A–B only if it is live, matching, and covers both products' target snapshots. A TestCase with no matching run is shown as `definition only`, never as passing. | Spec §11.1; AGENTS.md §7. Proved by M09-T03 and M09-T04. |
| D7 | **Code completeness and restricted dependencies.** Context units carry `code_completeness` (`complete-unit` or `excerpt`) from `partKind`, fixing the M07 loss at `units.py:344`. Markdown fences use the M06 info line, `python complete unit` or `python excerpt`. A referenced dependency whose definition part is unreadable, unindexed or unresolved appears in `gaps` as "dependency not included in returned material", naming only the readable referring occurrence's symbol text as shown in the readable target code. The reason is given only when a readable `UnresolvedReference` or `ImportIssue` states it. Nothing distinguishes hidden from missing. | Spec §11.5; A22 "restricted/partial code is not presented as complete". Proved by M09-T06. |
| D8 | **Budget.** Reuse the M07 whole-unit byte budget and continuation. One code part is one unit. A unit larger than the maximum returns 422 `C1-CX-010` with the minimum bytes and is never truncated. Section order is fixed. Within a section, units are ordered by target member order, then symbol key or document order key, then ID. | M07 D7–D8. |
| D9 | **Fixture extension `software-integration` v1.1.** ledger a1's `create_invoice` accepts `amount == 0`. The contract and `docs/invoicing.md` say "amount must be greater than zero; zero is rejected with 422". a2 fixes this, alongside the M08 a2 changes. The fixture adds: a reviewer (carol) `discrepancy` assertion with TextQuote evidence on both parts; `CONTRIBUTING.md` "Running tests" parts linked by `executionInstructions` (a command in a code block, rendered but never run); a `conftest.py` fixture linked by `fixtureOf`; and one existing TestCase for `create_invoice` with a run on a2 only. Expected goldens for Carol and Dave are specified independently. | PLAN M09-T02 and M09-T05. M08 D13 fixture design is extended, not replaced. |
| D10 | **External consumer demonstration** (`scripts/demo_m09_consumer.py` and `fixtures/software-integration/consumer/`). A deterministic, non-LLM consumer requests the conformance package for `create_invoice` at target {a1, b1}. It checks that the reviewed, checked-in test `test_invoice_zero_amount_rejected.py` cites the evidence IDs of the normative part in the returned package; the test's header lists the evidence IDs it was written from. It then checks out a1 and a2 from the fixture git repositories into a temporary directory and runs that test there with pinned pytest, outside the C1 service, with AI variables unset and no network. It imports the JUnit results as TestRuns through `c1-svc-ci`. The expected results are **fail** on a1 and **pass** on a2. C1 never runs code, and the runner never runs code taken from a C1 response. | A18; PLAN M09-T05 ("tests the fixture evidence, not LLM coding quality"). |
| D11 | **Security.** Selecting `test-development` grants nothing. Each record is authorized independently. Execution instructions, comments and README text are data only. Citation expansion uses generic authorized reads, so hidden parts return the uniform 404. Structured and Markdown output contain the same authorized items only. | AGENTS.md §5.3, §9; spec §13.4. Proved by M09-T06. |
| D12 | **Owner-approved request budget change (2026-09-30).** The first M09 regression gate failed once, at M08-T01, with a fail-closed 503 `C1-SW-007` (`time_budget`). Profiling ([diagnostic](../evidence/M09/first-request-diagnostic.json), `docs/evidence/M09/lookup-profile.py`) showed that every authorized request re-verifies each readable resource's current binding and `can_read` twice in OpenFGA: once in plan build and once in finalize (M05 design). With the software fixture, that is about 630 resources for Carol and about 3.5 s per request, against the 5,000 ms default. Optimizing TerminusDB layers made no difference. On the owner's explicit choice, the default `C1_QUERY_TIME_BUDGET_MS` changes from 5,000 ms to 10,000 ms. The planner default changes with it, and the harness and loader client timeouts keep their +10 s margin. The 30,000 ms cap and all fail-closed behavior are unchanged. This supersedes the 5,000 ms default of M07 D22; earlier acceptance texts are not rewritten. The linear per-resource verification cost is recorded as a limitation for a later milestone. |
| D13 | **Configurable timeouts for slow hosts (owner instruction, 2026-09-30).** The first three gate attempts on the development laptop failed from host swap exhaustion; the evidence is under `docs/evidence/M09/attempt*`. The owner therefore directed that the gate run on makako.sf.nethserver.net, with larger minimum delays because that machine is slower. The M07 run on makako had failed even at the 30,000 ms budget, because two timeouts were fixed: OpenFGA's own 3 s server deadlines and C1's 5 s OpenFGA/OIDC client timeouts. Both are now configurable with unchanged defaults: `C1_BACKEND_TIMEOUT_S` (default 5 s, range 1–30 s) for the C1 clients, and `C1_FGA_DEADLINE` (default `3s`) for `OPENFGA_REQUEST_TIMEOUT` and `OPENFGA_LIST_OBJECTS_DEADLINE` in `deployment/compose.yaml`. The makako gate sets the request budget to 30,000 ms, the backend timeout to 30 s, and the OpenFGA deadline to `30s`. Fail-closed behavior is unchanged. |

## 7. Recovery and security

| Failure point | Expected safe behavior and recovery |
|---|---|
| Target member unreadable or changed during continuation | 409 `C1-CX-011` restart; no substitution. |
| Required target or goal missing | 400 `C1-CX-001` naming only the missing field. |
| Anchor has no definition in the target | `unresolved` outcome with the readable anchor, never a definition from another snapshot. |
| Dependency expansion reaches its cap | Truncation reported in `bounds`; no partial unit is presented as complete. |
| External runner failure | Recorded as a TestRun with `error` result, or not imported. C1 state is unchanged either way. |

The external runner runs only checked-in fixture code in a temporary directory, with no network and no environment secrets.
