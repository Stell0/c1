**Conflicts and their resolution.**
1. **Reserved name.** Lifting the `software` reservation is the planned M08 action (M02 D11), not a scope change.
2. **No in-place profile upgrade.** A same-name profile upgrade reconciles to a duplicated class set and ends in 503. M08 therefore installs `software` 1.0.0 once. Later milestones add separately named additive profiles, such as `software-applicability` in M11, rather than versions of `software`. The upgrade defect is recorded as a limitation, not fixed here.
3. **Class-ranged references are only loosely checked.** At write time a class-ranged reference only proves that the target exists and is readable, not its class. The software service therefore checks every structural reference's class at read time, and treats a mismatch as unresolved (D9). A generic write-time class check changes behavior for existing profiles, so it is deferred and recorded.
4. **Stale SCIP URL.** The spec and architecture cite `sourcegraph/scip`. The pinned artifacts cite the current `scip-code/scip` location. No requirement changes.

## 2. Goal and boundaries

**Observable result.** An installed data-only `software` profile represents two synthetic Python products. This includes their repositories, immutable snapshots, releases, logical symbols and per-snapshot occurrences, a capability shared by both, an explicit OpenAPI contract, documentation per target, test definitions and test runs, and import coverage with errors and unresolved relationships. Everything is ingested through ordinary authenticated ChangeSets by deterministic producer clients. Target sets pin one snapshot per repository, plus a contract version and a configuration, independently of the C1 knowledge revision. A small software read API resolves a declared target set and returns only records that correspond to it, each resolvable to an immutable snapshot, path and range or digest. It never guesses a "latest" version, and never reveals hidden paths, files or counts.

**In scope.**
- The `software` profile and ADR-0017.
- The target-set model.
- Producer import contracts: SCIP JSON subset, OpenAPI 3.1 subset, documentation, and JUnit-derived test runs.
- The coverage and issue model, and idempotent imports.
- The software read API: target resolution and target-pinned lookup.
- The `software-integration` fixture: two tiny git repositories with deterministic commits, and the checked-in SCIP JSON.
- Three producer service principals and the deterministic producer demonstration.

**Out of scope.**
- Context profiles for software tasks (M09–M11). No change to `/v1/context`.
- Applicability states, review-candidate rules and documentation drafts (M11).
- AsyncAPI, and languages other than Python.
- Running any indexer, compiler, test runner or CI inside C1, and any network fetch by C1.
- Production or company-wide ingestion.
- Write-time class-range enforcement, and repair of the profile-upgrade defect.

**Invariants touched.**
- AGENTS.md §4.1: identity independent of names; no merging by matching names; separate time from source version.
- AGENTS.md §5: every software record is independently authorizable, and current bindings govern historical snippets and coverage.
- AGENTS.md §6: bounded, deterministic, revision-bound pagination.
- AGENTS.md §7:
  - Target pinning.
  - Structural versus interpretive versus observed evidence.
  - A test file is not a passing run.
  - Partial ingestion is explicit.
  - A branch URL is not evidence.
  - Stored commands never execute.

| D3 | **Logical symbol versus occurrence (SCIP v0.10.0 subset).** `CodeSymbol` stores `repositoryRef`, `scipScheme`, `packageManager`, `packageName` and `descriptors`, which is the descriptor suffix of the SCIP symbol string. The SCIP package *version* is excluded from the logical key, because it changes across snapshots. The producer reuses a readable symbol that has the same repository and key; symbols in different repositories are always distinct, even with identical descriptors. Document-local SCIP symbols (`local …`) never become CodeSymbols; they are counted as out of scope in coverage. A `SymbolOccurrence` stores `symbolRef`, `snapshotRef`, `fileRef` (the file's Document), `partRef` (0..1, the enclosing code part), `role` (one or more of definition, reference, import, write-access, read-access, test, generated, forward-definition, from SCIP `SymbolRole` bits) and a half-open zero-based range (`startLine`, `startCharacter`, `endLine`, `endCharacter`) with `positionEncoding` utf-8, utf-16 or utf-32. | D4 | **Files and code as M06 documents.** Each analyzed file at a snapshot is a `Document`: `dcterms:title` is the repository-relative path, `sourceRevision` is the commit ID, and `contentDigest` is `sha256:<hex>` of the exact file bytes. Its parts are top-level code units: one `code-unit:python` part per module-level function or class, in source order, with exact text, plus a leading `code:python` part for remaining module text. The producer computes part boundaries from SCIP definition ranges. Order keys are fixed-width, zero-padded source-order ranks. Citation evidence cites a part with a TextPosition selector and `sourceRevision` equal to the commit ID (M06 D8). Line numbers are carried by the occurrence range, never by evidence. A Source per snapshot (`sourceKind` `git-snapshot`, locator `git:<repo-key>@<commitId>`, revision equal to the commit) is linked from each file Document by `dcterms:source`. Proved by M08-T03. |
| D5 | **Target sets.** A `TargetSet` record has `snapshotRef` (1..n, at most one per repository), `contractRef` (0..n Documents at a declared contract version), `configurationRef` (0..n), and a `label`. A `Configuration` stores a name and sorted `key=value` parameter strings with a digest. Target sets are independent of the C1 revision: the same target set can be read at any knowledge revision, and current bindings apply. A request may instead supply an *inline* target set of the same shape. Branch names are accepted only in `POST /v1/software/targets/resolve`, which resolves each (repository, branch) to the snapshot of the latest readable `BranchObservation` at or before a caller-supplied `as_of` timestamp and reports the resolution. Unknown compatibility between members stays `unknown`; M08 records no compatibility claims. | Spec §10.2 (explicit and reported defaults, no undefined latest); architecture §12.2 target elements. | D6 | **Relationship predicates carry their basis.** Every relationship is an ordinary Assertion with `origin`, attribution and `prov:wasGeneratedBy` pointing to the import Activity. | D7 | **Interface contracts: OpenAPI 3.1.1 JSON subset.** The contract file is a Document with `partKind` `code:json`. | D10 | **Import contract, coverage and completion rules.** Each producer run is one core `prov:Activity` (toolName, toolVersion, method in {`scip-occurrences`, `ast-calls`, `openapi-operations`, `docs`, `junit-runs`}, `used` pointing to the snapshot's Source) plus one `ImportCoverage` record per *scope* touched. ## 7. Recovery and security

| Failure point | Expected safe behavior and recovery |
|---|---|
| Profile install interrupted | The ADR-0012 two-commit guard applies: readiness fails closed, and recovery completes or reports the schema/marker state. Software routes stay 404 until the marker exists. |
| Producer batch fails mid-run | Earlier batches remain. No coverage record is written, so coverage is `unknown` for that run. A rerun with the same deterministic keys replays completed batches and continues. Records are never deleted. |
| Invalid SCIP, OpenAPI or JUnit input | The producer writes ImportIssue records and `partial` or `failed` coverage. The C1 service receives only ordinary validated records. |
| Target member hidden, missing, or of the wrong class | Same 404 or `unresolved` outcome, carrying no hidden detail. |
| Branch observation absent at `as_of` | `unresolved` with reason `no-observation`; never falls back to another snapshot. |
| Secrets | New client secrets are generated into the ignored `.env` by `make stack-up`. Fixtures and evidence contain none. SCIP metadata host paths are normalized before check-in. |
