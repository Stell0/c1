## 2. Goal and boundaries

**Observable result.** An external author (Bob) requests `documentation-update` for capability "Invoice creation" with the target {a2, b2, contract 1.1.0}. In one authorized package, Bob receives:
- the existing guide's structure with **per-part** applicability for that target;
- both products' responsibilities: the ledger handler and the shop client;
- the explicit interface contract, and the `implementsOperation`/`declaredCall` links that connect the two sides;
- the relevant configuration, matching test evidence, and known discrepancies and review candidates;
- an explicit `unknown` for any compatibility with no evidence.

Bob then submits a new draft through a ChangeSet into his drafting scope. The draft records:
- its target, lineage (`prov:wasDerivedFrom` from each draft part to the source parts it used), and author;
- its C1 review state, separately from external publication.

After review:
- An explicitly reviewed re-scope makes the draft readable by `sw-shared`.
- An imported publication result is the only record of external publication.

The old document history, its validity for a1/b1, and every unresolved difference remain.

**In scope.**
- Applicability states and records, and the mapping of earlier predicates onto them.
- An external deterministic review-candidate rule producer.
- The `documentation-update` profile.
- Draft records and lineage.
- Draft review and revalidation.
- The lineage-aware re-scope approval policy.
- External publication receipts.
- Fixture v1.3.
- The A20 demonstration.

**Out of scope.**
- Generating prose. C1 never writes documentation text.
- Git writes, pull requests or merges.
- Explorer workflows (M12).
- Automatic applicability inference from text.

**Invariants touched.** AGENTS.md §4.1 (preserve conflicting claims), §5.2, §5.3, §7, §9.

## 3. Decisions to resolve

| ID | Decision | Rationale, evidence, proof obligation |
|---|---|---|
| D1 | **Applicability states.** `software` profile 1.3.0 adds the record class `ApplicabilityRecord`. Its fields:<br>• `subjectRef`: a Document or DocumentPart.<br>• `targetSnapshotRef`: 1..n snapshots.<br>• `state` ∈ {`applicable`, `needs-review`, `not-applicable`, `contradicted`}.<br>• `basis` ∈ {`declared`, `rule`, `review`, `test`}.<br>• `ruleRef` (0..1), `activityRef`, evidence, and `reviewState`.<br>The absence of any readable record or declaration for a (subject, target) pair means `unknown`. The earlier declarations are kept as declarations and read as inputs, without migration: `describesSnapshot` counts as `applicable` (declared, document-level), and M10's `notApplicableTo` counts as `not-applicable` (declared). | Spec §10.5 lists exactly these distinctions and leaves the names to M11. Development data needs no migration (owner, 2026-09-29). Proved by T02 and T03. |
| D2 | **Effective applicability.** For each (part, target snapshot) pair, compute an effective state over readable inputs:<br>1. Part-level inputs win over document-level inputs.<br>2. Within the same level, the most cautious state wins: `contradicted` over `not-applicable` over `needs-review` over `applicable`.<br>The effective state decides only ordering and labels. **Every** contributing readable record is listed with its basis, attribution and evidence, so a disagreement is never hidden. A part is never marked globally obsolete: states are always relative to target snapshots. | Spec §10.5 and AGENTS.md §4.1. Proved by T02. |
| D3 | **Review-candidate rule (external, deterministic).** `scripts/doc_review_rule.py` (rule `doc-dependency-change/1`) runs outside C1 as the analyzer producer. Its condition: a document part P declares `documents` for operation O or symbol S, and between a described snapshot and a target snapshot, either the target contract's operation part digest differs, or the implementing symbol's definition-part digest differs. When that holds, it submits `ApplicabilityRecord(P, target, needs-review, basis rule)`, citing both parts as evidence. It never submits `contradicted`. Only an attributed review or matching test evidence submits `contradicted`, with that evidence. C1 runs no analysis. | Spec §10.5: "a dependency change can deterministically mark a review candidate, but does not prove that prose is false". Proved by T03. |
| D4 | **`documentation-update` profile.** A software-task profile; the anchor is a capability or operation, and `requires_target` is true. The target must contain snapshots of at least two repositories, or the request returns 400 `C1-CX-001`. Its fixed sections:<br>• interpretation and target;<br>• **document structure:** each readable part of each candidate document in order, with its effective applicability and contributing records;<br>• **responsibilities:** for each repository, symbols that implement the capability or operation, or declare calls to it, with M09 code units;<br>• **interface contract:** the target contract's operation parts, plus every explicit `implementsOperation` and `declaredCall` link;<br>• configuration; tests and runs (M09 labels); changes and discrepancies (`needs-review` or `contradicted` records, and `discrepancy` assertions);<br>• **compatibility:** for each pair of target snapshots, `unknown` unless there is a matching live run covering both (M09 D6), which is shown as observed evidence for exactly that pair;<br>• gaps, sources and bounds.<br>Matching names never create a link. | Spec §11.4, A20, and M11-T01. Proved by T01. |
| D5 | **Drafts and lineage.** A draft is a core `Document` with ordered parts plus a `DocumentationDraft` record. The record's fields:<br>• `documentRef` and `revises` (the old Document, 0..1);<br>• `targetSnapshotRef` (1..n) and `targetContractRef`;<br>• `authorRef`;<br>• `draftState` ∈ {`draft`, `submitted-for-review`, `approved`, `withdrawn`};<br>• `applicabilityCheckRef`: the Activity whose readable applicability evaluation for exactly the draft's target was current at approval.<br>Lineage uses part-to-part `prov:wasDerivedFrom` assertions, each with evidence. A draft adds records only. It cannot alter or delete the old document, its history, or any applicability or discrepancy record. | Spec §11.4 and §10.5 (retain old history, lineage and unresolved differences). Proved by T04. |
| D6 | **Draft approval and freshness.** Moving a draft to `approved` is an ordinary reviewed ChangeSet, with independent review. Validation requires that `applicabilityCheckRef` names a rule run whose recorded target equals the draft's current target. If the target changed, or the rule has since been re-run for that target, approval fails with `C1-CS-020 applicability_revalidation_required`. Missing compatibility evidence stays `unknown`, and approval does not change it. | Spec §11.4, "a changed intended source target requires applicability revalidation". Proved by T06. |
| D7 | **Quarantine and lineage-aware widening (owner decision).** A `DocumentationDraft` and its Document and parts must be created in a scope whose `kind` is `drafting`, and whose only reader and contributor is the author (plus explicitly granted reviewers). Creation in any other scope is rejected with `C1-CS-021 draft_requires_drafting_scope`. A re-scope of a draft resource requires approvals from:<br>(a) an access admin of the destination, as today, and<br>(b) an access admin of every scope currently bound to a lineage source part.<br>The proposer cannot approve. Each approver counts only for scopes where they hold `access_admin` at approval time. The lineage scope set is captured, with a digest, at proposal and recomputed under current bindings at apply. A difference, or an unreadable or unresolved lineage source, fails closed with 409 `stale_security_operation`. This is set coverage, never a scope ordering. | Owner decision 2026-10-01; AGENTS.md §5.2 and §5.3; M03 D7 re-scope protocol. Proved by T06 and T07. |
| D8 | **Publication receipts.** The `ExternalPublication` record has `draftRef`, `locator` (repository URL and commit, or a URL as data, never fetched), `publishedAt`, `publisherRef`, and an activity with evidence: the imported publication report. It is created only by an import ChangeSet from a publisher producer (`c1-svc-ci` in the fixture). A draft's external publication state is derived only from readable `ExternalPublication` records. A C1 approval or commit never sets it. | Spec §10.5 and §11.4; AGENTS.md §7. Proved by T05. |
| D9 | **Fixture v1.3 (data only).**<br>• `docs/invoicing.md` parts get part-level `documents` claims: "Creating an invoice" documents `createInvoice`, and "Reading an invoice" documents `getInvoice`.<br>• A run of the rule over the target {a2, b2, contract 1.1.0} marks only the createInvoice part `needs-review`, because the contract field changed from `customer` to `customer_id`. The getInvoice part stays applicable by declaration.<br>• A drafting scope `drafts-bob` (Bob: reader and contributor). Access admins: Frank for `sw-shared`, Erin for `sw-ledger` and `sw-shop`.<br>• Bob's draft, "Invoicing (1.1)", whose lineage cites the a2 contract part, the a2 `create_invoice` part and the b2 `post_invoice` part.<br>• A publisher run that imports one publication report.<br>The expected outputs for Bob, Carol, Dave and Alice are written independently in the tests. | Spec A20; M09 precedent. |

## 7. Recovery and security

| Failure point | Expected safe behavior and recovery |
|---|---|
| Re-scope proposal while lineage sources are pending a security operation or are unreadable | Refuse with 409; nothing changes. |
| Lineage bindings change between proposal and apply | 409 `stale_security_operation`; re-propose. |
| A rule producer is interrupted | Its records are applied per batch (M08 rules); `unknown` remains where it never wrote. |
| A publication import fails | No `ExternalPublication` record; the state stays `not-published`. |
| Untrusted text in drafts or reports | Inert rendering; locators are never fetched. |
