## 2. Goal and boundaries

**Observable result.** `POST /v1/context` returns, for an anchor and declared topics under a versioned data-only path profile, a Markdown package and an equivalent structured package built from one authorized selection: interpretation, orientation paths, self-contained facts with values, units, conditions, time, review state and origin, available excerpts, resolvable citations, provenance that separates original sources from importing activities, disagreements, gaps for requested fields, and budget bounds with signed continuation. The cross-project-batteries fixture shows PaperTrader and Robotelier producers sharing one canonical Tesla company and a third consumer obtaining battery context without choosing a project, without AI credentials, and without a battery that lacks the Tesla keyword being lost or an unrelated product being included.

**In scope.** Request grammar; context profiles as data with allowed typed paths; controlled topic scheme (`topics` profile) and alias resolution with explicit ambiguity; selection, grouping, deterministic ordering, evidence units; budget and continuation; Markdown and structured renderers; citation encoding; the fixture with golden outputs.

**Out of scope.** Natural-language query planning, semantic or vector search, LLM summaries, automatic synonym expansion, software target sets and the four software task profiles (M08–M11; this milestone leaves declared extension points for them in the profile schema without implementing them), browser preview (M12).

**Invariants touched.** AGENTS.md §6.1 (exact keywords unchanged; graph context is a separate explicit mode with declared paths; report ambiguity and matched paths), §6.2 (immediately usable material; same selection for both formats; never claim unavailable information does not exist; budgeting preserves qualifications and conflicts; no inference, no LLM), §5.3 (hidden edges, evidence, titles, excerpts, and topic labels never enter the package or its explanations).

## 3. Decisions to resolve

| ID | Decision | Rationale, evidence, proof obligation |
|---|---|---|
| D1 | **Request grammar** (strict model, unknown keys 400 `C1-CX-001`): `profile` (name from the trusted context catalog), `profile_version` (exact), `anchor` = `{id}` or `{label, language?}` (exact normalized label or alias match among readable entities), `topics[]` (controlled labels resolved in the profile's topic scheme, or Concept IRIs), `keywords_all[]`/`keywords_any[]` (optional exact narrowing with unchanged M05 semantics), `fields[]` (declared field names of the profile; unknown names 400), `project_ref` (narrowing only), `revision`, `formats` ⊆ {`markdown`, `structured`} (default both), `budget: {unit: "bytes", maximum}` (2 048 ≤ maximum ≤ 524 288; default 65 536), `cursor`. `POST` is read-only; the route sets no state and creates no ChangeSet. | Architecture §7 illustrative request; spec §6.2 "identifies an anchor entity or explicit selectors, a topic/aspect, a versioned data-only path profile, optional filters, output format, and size budget". |
| D2 | **Context profiles as data** in `profiles/context/<name>.json` (trusted catalog like `profiles/available`, versioned, digested, listed by `GET /v1/catalog`): `name`, `version`, `anchor_types[]`, `topic_scheme` (Concept scheme IRI), `topic_predicate` (`dcterms:subject`), `paths[]` each `{steps: [{predicate, direction: out|in, target_types[]?}], max_depth}`, `fact_predicates[]` or `"declared"` (all declared literal/IRI predicates of the matched node's profile), `qualifier_predicates` (`c1:validDuring`, plus profile-declared `unit`, `conditions`, `measuredOn`), `fields: {name → predicate or path}` (for gap reporting and M09–M11 aspects), `group_by: node`, `order: distance,label,id`, `sections` (fixed template identifiers, no free text). A profile contains no code, expressions, or prompts; loading validates it against a JSON schema and rejects unknown keys (`C1-CX-002`). First profile: `graph-context` v1 with paths `hasProduct → hasComponent → hasVersion` (depth 3) and topic predicate `dcterms:subject`. | Architecture §11.1 "approved declarative selection/path/order/presentation data … not arbitrary executable code"; AGENTS.md §6.1 allowlisted typed paths. ADR-0016. |
| D3 | **Topic scheme** as data-only profile `profiles/available/topics/` (`Concept` class with `skos:prefLabel`, `skos:altLabel`, `skos:inScheme`, `skos:broader`). Topic resolution: normalize the requested label with `c1-kw-1` and match readable Concepts' `prefLabel`/`altLabel` exactly (language-aware when given); zero matches → `unresolved` outcome (no package, HTTP 200 with `outcome: "unresolved"`); more than one → `ambiguous` with the readable candidates; `skos:broader` is followed only when the profile sets `topic_expand: narrower` (default off; `graph-context` v1 keeps it off). A node "carries" a topic when a readable active assertion `node dcterms:subject Concept` exists. Topic resolution never changes keyword matching. | Spec F02 "A declared topic scheme may explicitly map alternative labels to one concept for graph-context retrieval. That separate mode MUST NOT change exact keyword semantics." |
| D4 | **Anchor resolution.** `{id}` must be a readable entity of an allowed anchor type, else 404 identical to nonexistent. `{label}` matches readable entities by exact normalized `prefLabel`/`altLabel`; one match resolves, several → `ambiguous` with readable candidates (id, primary label, types), none → `unresolved`. Redirected (merged) entities resolve to the survivor only when the redirect is readable (M05 rule). | Spec §6.2 "Ambiguous selectors remain ambiguous"; F01 redirect authorization. |
| D5 | **Selection.** (1) Build the M05 authorized selection at the requested revision (all readable candidates). (2) Traverse from the anchor with the profile's predicates and depth using `traverse_authorized`; keep every reached node with its path (the sequence of readable assertion IDs). (3) Matched nodes = reached nodes that carry at least one resolved topic; when the request has no topics, matched nodes = reached nodes of the profile's `target_types`. (4) Apply `keywords_*` and `project_ref` narrowing to matched nodes with M05 semantics. (5) Orientation nodes = nodes on a path to a matched node (kept for explanation only, no facts). (6) Facts = readable active assertions whose subject is a matched node and whose predicate is in `fact_predicates`; relationship facts include the object only when readable. (7) For each fact: readable evidence, its Source record (title, kind, revision), importing activities, selector and excerpt: producer `excerpt` on the evidence when present, else the selected text from the readable part (M06 contract), else none. (8) Qualifiers: `validDuring` interval, review state, origin, confidence, and profile-declared qualifier predicates asserted about the same subject with the same measurement node. Unreadable evidence, parts, sources, or topic assertions are simply absent; they never appear in explanations. | Spec §6.2 example (company → product → battery; battery without Tesla keyword matches; nearby unrelated nodes excluded); §6.3 rows; AGENTS.md §5.3. |
| D6 | **Evidence units, grouping, conflicts, duplicates.** A unit = all readable facts of one matched node for one predicate (all competing assertions together) with their evidence and qualifiers; units are indivisible for budgeting. Competing assertions (same subject and predicate, different object) are rendered together under a `disagreement` marker with each claim's source and review state; a declared single-valued predicate adds the M04 conflict basis; legitimately multi-valued predicates are listed without a conflict marker. Corroboration: evidence records pointing to the same Source **and** the same `sourceRevision` are one original source; the unit shows `sources: 1` and `imports: n` with the activities, never `n` independent confirmations. Incomplete measurements (a quantity without a unit or without required conditions per the profile) are shown with `incomplete: [unit]`. Product, version, quantity, unit, and conditions stay separate fields; no unit merges values across versions. | Spec §6.3 "Repeated source ingestion is not independent corroboration"; A05; AGENTS.md §4.1. |
| D7 | **Ordering.** Units are sorted by (path distance from anchor, matched node normalized primary label, matched node IRI, predicate IRI); within a unit, assertions by (review state order `confirmed` < `reported` < `disputed`, source title normalized, assertion IRI); citations numbered in first-use order. Identical inputs and security state give identical output; only `generated_at` and `request_id` are declared volatile. | Spec §6.3 determinism; PLAN M07-T06. |
| D8 | **Budget and continuation.** Unit `bytes` = UTF-8 length of the unit's Markdown rendering (the structured form mirrors the same units). Fixed sections (interpretation, orientation, sources index for included units, gaps, bounds) are always included; if their size alone exceeds `maximum`, the response is 422 `C1-CX-010 insufficient_budget` with `minimum_required`. Units are added in D7 order while cumulative size ≤ maximum; the first unit that does not fit and all later units are deferred whole (never split; qualifications and disagreements of an included unit are always included). `bounds` reports `truncated`, `deferred_units` (count of authorized units, permitted metadata), and `next_cursor` = M05 signed cursor binding revision, request digest, and the unit offset; a continuation rebuilds the selection under current authorization and returns 409 `C1-CX-011 restart_required` if any unit before the offset changed (revocation, re-scope, or new authorization), never reusing earlier permissions. | Spec §6.3 "Budgeting must preserve essential caveats"; architecture §11.3; PLAN M07-T06/T07. |
| D9 | **Citations and provenance.** Each fact carries `citations[]` `{n, evidence_id, source_id, source_title, source_kind, source_revision, part_id?, selector?, excerpt?, imported_by: [activity_id], corroboration: independent|duplicate_import}` where every identifier resolves through existing routes (`/v1/evidence`, `/v1/sources`, `/v1/documents/{id}/parts`, `/v1/resources/{id}`); Markdown uses `[^n]` footnotes and a `Sources` section `n. *title* (revision) — evidence <id>; imported by <activity ids>`. Attributed manual statements are cited as `manual statement by <attributed_to>`; stored externally authored explanations (assertions of origin `derived` with an activity) appear with their attribution and never as C1's conclusion. | Spec §6.3 Sources and Provenance rows; §4.3. |
| D10 | **Markdown and structured rendering.** Fixed section order: `# Context: <anchor label>`, `## Interpretation` (profile, version, revision, resolved anchor, resolved topics, ambiguity notes, narrowing filters), `## Orientation` (paths as `A → predicate → B` with labels; only readable nodes and assertions), `## Facts` (grouped by node, then predicate; each claim as value + datatype/unit + conditions + valid time + review state + origin + footnotes; disagreement blocks), `## Text` (excerpts as blockquotes with footnotes, code excerpts as fenced blocks labeled `excerpt`), `## Disagreements` (index of units with competing claims), `## Gaps` (`fields` requested but absent from the returned authorized material, phrased exactly as "not present in the returned material"), `## Sources`, `## Bounds`. All text is escaped with the M06 rules; no images, links, or HTML. The structured form is a JSON object with the same sections, unit IDs, and citation numbers, plus `format_parity_digest` = SHA-256 of the canonical JSON of the selected unit and citation identifiers, which is also embedded as an HTML-comment-free footer line in the Markdown so parity can be checked. | Spec §6.3 package elements; PLAN M07-T05. |
| D11 | **Fixture `cross-project-batteries`** (`fixtures/cross-project-batteries/`): profiles `batteries` (predicates `hasProduct`, `hasComponent`, `hasVersion`, `hasInstrument`, `capacity`, `energyDensity`, `unit`, `conditions`, `measuredOn`, `cycleLife`; class `Measurement`) and `topics` (Concepts `batteries`, `energy storage` with alt label `storage`, `vehicles`, `financial instruments`). Scopes `bat-papertrader`, `bat-robotelier`, `bat-shared`, `bat-hidden`. Producers: `c1-svc-papertrader` creates Tesla (company, in `bat-shared`), instrument TSLA-synthetic (`hasInstrument`, topic financial instruments), and a revenue claim; `c1-svc-robotelier` resolves Tesla by exact label through `GET /v1/entities` and reuses its ID, then creates products Optimus-synthetic, Vehicle-synthetic, Megapack-synthetic, Solar-tile-synthetic (topic none), battery versions O-B1, V-B2, M-B3 (topic batteries) with measurements: V-B2 has keyword `tesla`; M-B3 has keywords `megapack`, `storage` but not `tesla`; M-B3 capacity has two competing claims (synthetic 3.9 and 3.6 with unit and conditions) from two different Sources; O-B1 capacity has one Source imported by two activities (duplicate import); V-B2 energy density lacks a unit (incomplete); datasheet Document with a public part containing the capacity sentence (evidence with `TextQuoteSelector`) and a `bat-hidden` part; hidden relation: Tesla `hasProduct` Prototype-synthetic and battery P-B4 in `bat-hidden`. Consumer `dave`: reader of `bat-shared`, `bat-papertrader`, `bat-robotelier`; reviewer `carol` approves all ChangeSets. All values synthetic. Golden: `expected/context-dave.md`, `.json`, `expected/keywords-all.json`, `expected/context-carol.md`, `expected/ambiguity.json`. | PLAN §4 fixture family; A15; architecture §11.4. |
| D12 | **Endpoints and layout.** `POST /v1/context`; `GET /v1/catalog` gains `context_profiles` (names, versions, digests, anchor types, fields). `src/c1/context/` (`request.py`, `profiles.py`, `topics.py`, `resolve.py`, `select.py`, `units.py`, `budget.py`, `markdown.py`, `structured.py`, `service.py`), `src/c1/api/routes/context.py`, `profiles/context/graph-context.json`, `profiles/available/topics/`, `profiles/available/batteries/` (fixture-only predicates stay in `fixtures/cross-project-batteries/profile/` and are installed by the loader, mirroring `directory`). No new dependency; no model, embedding, or provider configuration name appears anywhere. | Architecture §3 (Context Builder over query and document services), §17. |
| D13 | **Limits.** Traversal reuses M05 bounds (depth ≤ 3, nodes ≤ 500, edges ≤ 2000, 2 s); units ≤ 500 per request (`C1-CX-012 too_many_units`, explicit, with the advice to narrow topics); excerpt length per citation ≤ 4 KiB (longer text is cut at a code-point boundary and marked `excerpt_truncated`, which is a bound, not a hidden-content signal). | Spec §6.1 "profiles cannot evade global bounds". |

## 7. Recovery and security

| Failure point | Behavior |
|---|---|
| Traversal budget or 2 s deadline exceeded | 503/422 with no partial package presented as complete; advice to narrow topics. |
| Profile catalog file invalid at startup | Readiness stays 503 until fixed; no fallback to an implicit profile. |
| M06 part contract differs from the assumption | Excerpt extraction is adapted in `select.py` only; the package contract and tests do not change. |
| Golden drift | Regenerated only by explicit command and reviewed. |

Secrets: none new. The builder never contacts the network; a local counter in T03 proves it during rendering. No positive authorization cache; every continuation rebuilds the selection.
