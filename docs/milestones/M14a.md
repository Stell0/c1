# M14a — Performance hardening

**Status:** IN_PROGRESS. The owner approved the plan and the roadmap insertion on 2026-10-05 ("Before implementing M15, I want you to plan on how we can improve speed…"; the plan was approved in plan mode).
**Roadmap contract:** [PLAN.md](../../PLAN.md) §M14a.
**Prerequisites:** M13 `VERIFIED`. The M14 makako results are the "before" measurement; the M14 report is written when that run finishes.
**Tests:** M14a-T01 equivalence, T02 round-trip budgets, T03 measured improvement against the targets in "Verification", T04 no authorization cache.

## Context

The M13 bench and the M14 benchmark on makako (4 vCPU, the declared measurement host) show C1 is too slow for realistic use. M14 scale S is 932 records; the tested principal reads 854.

| Observation (makako) | Value |
|---|---|
| Any simple read: alias lookup (1 hit), keyword, label prefix, valid-at, documents | ~8 s median, 57 OpenFGA calls each, independent of result size |
| `graph-context` at 64 KiB / a refused (422) context | 23.5 s / 5 s |
| Entity list: 900 readable resources / 3,000+ | 16.8 s / 503 (30 s budget exhausted, before the 5,000 limit) |
| ChangeSet apply: 1 / 200 creates | 32 s / 126 s |
| ChangeSet of 36 replaces (validate / apply) | 150 s / 1,359 s (outlived the 300 s proxy timeout) |
| Corpus load, 932 records in 5 ChangeSets | 462 s |

The code was traced end to end. The slow points are structural round-trip multipliers, not slow individual queries. The goal is to cut round trips while keeping every security invariant:
- current-binding authorization stays fresh on each request (no positive authorization cache — AGENTS.md §5.3, ADR-0013, ADR-0020);
- reads fail closed;
- outputs stay byte-identical: the M07 goldens and M14 security invariance must still hold.

## Root causes (ranked by measured impact)

**Reads** (path: `query/service.py` → `query/plan.py` → `query/compile.py`)

1. **Content fetch fans out across classes.** `fetch_records` sends every authorized ID to almost every declared class:
   - `_fetch_records_content` in `compile.py:285-352` issues one GraphQL POST per class per 200 IDs;
   - only the canonical-kind classes are skipped (`storage/mapping.py:34-89`);
   - current reads never pass `storage_types` (`service.py:227`).

   That is about 121 POSTs per request at N = 854, against a 1.5-CPU TerminusDB. All content is re-fetched on every request, even though content at a commit is immutable.
2. **Authorization runs twice over all N.** Build and `finalize` (`plan.py:105-143, 209-259`) each issue ⌈N/50⌉ BatchChecks plus a binding source. `use_scan` (`plane.py:19-27`) estimates scan pages from the journal binding count, and scan pages are strictly sequential (`fga.py:202-232`). OpenFGA calls total 1 + 2⌈N/50⌉ + 2S, which is 57 at S.
3. **Fixed per-request reads.**
   - `assert_installed_profiles` (`storage/schema.py:179-217`) runs on every fetch: a full schema GET, P marker GETs, and a schema regeneration in Python.
   - About 4–5 workflow `head()` calls per request.
4. **CPU.**
   - `_project_records` is O(N²): it rebuilds a frozenset per ID per pass (`service.py:331-341`).
   - `evaluate_entity` recomputes the active assertions for each entity (`filters.py:443`).

**Context** (`context/budget.py`, `select.py`)

5. `build_page` renders **every** prefix with no early exit (`budget.py:134-152`), plus a cursor and checkpoint hash for each. That is O(U²) markdown and JSON work, and it also runs on the 422 path.
6. `select_context` rebuilds the adjacency for every frontier node (`select.py:438-452`, `query/traverse.py:142-149`).

**Writes** (`changes/apply.py`)

7. **`Terminus.get_record` inside `_permission`** (`apply.py:275-279`) is called for every replace on every permission pass: 1 in validate, 2 in approve, 8 in apply, plus 1 per ChangeSet read. Each call is about 18–45 *sequential* per-class GETs plus `assert_installed_profiles` (`terminus.py:284-321`). At 36 replaces that is about 13,000 GETs in apply.
8. **Per-resource checks**, 5 sequential round trips each, unbatched: `check_read`/`check_operation` → `check_many` with a single ID. `_visible` in apply uses its own memo (`apply.py:1311`), external references are checked without a memo (`:1230`), and reconcile repeats the passes three times.
9. **Full workflow listing after every journal write.** `Journal._versioned_entries` → `documents_at_version` (`journal.py:170-180`) downloads every envelope — Operations with full payloads, Idempotency entries, reports — after each `_save`. That gives a 4–5 s floor per workflow step, and it grows with history.
10. **Per-binding OpenFGA calls**: 4 sequential calls per binding in `_reconcile` (`apply.py:1592-1602`); a per-create `journal.get("Binding")` (`:1185`); a per-binding `plane.bindings` in `_finish` (`:1790`); and a full `/api/log` scan in `_receipt` on every fresh apply (`:1085-1119`).
11. **`GET /v1/instance` runs `Runtime.ready()` twice** (`api/routes/system.py:49-52`). That is about 40 round trips, including OIDC/JWKS, `detect_installed_registry` and the journal listing. Clients and the benchmark call it to get the head.

**Operations**

12. TerminusDB delta layers are never optimized. In M13, the workflow listing dropped from 0.56 s to 0.15 s after `optimize`, and `/api/log` on the 685-commit workflow DB took 9–15 s.

## Proposed changes (in implementation order; each is independently measurable)

### Phase A — measurement first

- **A1 Round-trip counters.** Count TerminusDB and OpenFGA calls per request in `Terminus._request` and `FGA` (a contextvar per request), and emit them in the existing audit line (`api/deps.audit`). Add unit "round-trip budget" tests: fake transports assert call counts for an entity list, a context build, and a 1/36-replace apply. These are regression guards.
- **A2 Baseline.** Use the M14 makako results (`results-S.json`, and M when the run finishes) and the M13 `bench.json` as the before numbers. Every phase is judged with `python -m benchmark compare` (performance warnings and family medians), with fidelity and security still 1.0.

### Phase B — reads (biggest win, low risk)

- **B1 Commit-keyed content cache plus a type index.**
  - Add an in-process, bounded LRU of decoded `NodeRecord`s keyed by `(commit_id, resource_id)` in `query/compile.py` (`fetch_records`), plus a per-commit `id → storage class` map.
  - Content at a commit is immutable, so this is a content cache, not an authorization cache: authorization still runs fresh, and only authorized IDs are ever looked up.
  - On a miss, fetch with `storage_types` hints from the type map (only one class per ID). Fill the type map from the previous commit's map plus the classes written by known ChangeSets (`CurrentBindingIndex.history_manifest` already carries them; see `documents/service.py:73-113`). Fall back to all classes for unknown IDs.
  - Expected effect: a warm read at an unchanged head does zero content fetches; a cold read issues about ⌈N/200⌉ per class present instead of about C × ⌈N/200⌉.
- **B2 Schema authority per knowledge head.** Memoize `assert_installed_profiles` by the knowledge commit read in the same request. The schema can change only through a commit. Readiness keeps the fresh read (ADR-0020 D4).
- **B3 Binding-source choice.**
  - Fix `use_scan` to compare *sequential* scan pages with ⌈N/concurrency⌉, using the measured tuple count (all tuple kinds), not the journal binding estimate.
  - Raise per-object read concurrency (configurable, default 32) on the reference deployment. Measure the OpenFGA CPU.
  - Keep the two authorization passes: `finalize` is the freshness guarantee.
- **B4 CPU fixes.** Compute the `visible_ids` frozenset once per pass in `_project_records`, and precompute the active assertions per subject once per request for `evaluate_entity`.
- **B5 Fewer heads.** Remove repeated workflow `head()` calls within one `check_many`/plan step where the same version is already pinned. Keep the before/after head comparison that makes the step fail closed.

### Phase C — context

- **C1 `build_page` early exit.** Rendered size is monotonic in the prefix length; prove it with a unit property test over the fixtures. Replace the linear all-prefix loop with a binary search for the largest fitting prefix. Compute the 422 `minimum_required` from the 1-unit render. Output must stay byte-identical: M07 goldens, M07-T06 determinism, M14 context family.
- **C2** Build each path step's adjacency once in `select_context`, and reuse it for every frontier node.

### Phase D — writes

- **D1 Replace targets fetched once.** In validate, approve, apply and reconcile, load every replace target with one `fetch_records(ids, revision=changeset.base_revision)` and pass the dict into `_permission`/`_visible`. Base equals head when apply proceeds (`apply.py:1357`). This removes the 8·N_R `get_record` calls.
- **D2 `get_record`** uses the B1 type map. Fallback: probe classes concurrently, still detecting collisions. ADR-0017 notes the earlier per-ID probe problem.
- **D3 Batched decisions.** For each (principal, relation), call `plane.check_many(..., batch=True, excluding=…)` once over all targets and references and pre-seed `_DecisionMemo`. Share one memo between `_visible(p)` and the `_require_all` passes within a step. This was the M09a D3 item, recorded but never wired.
- **D4 Incremental journal snapshot.** After the process's own `save_many`, update `_snapshot`/`_view` in place when the save's base equals the cached version. The single writer makes this safe; a version mismatch still triggers a full listing.
- **D5 Batched publication.**
  - `bound_to_many` for the pre-read and the confirmation, and batched `fga.write` (≤100 tuples), in `_reconcile`.
  - Use a single `journal.view()` for the binding lookups in `_planned_records` and `_finish`.
  - In `_receipt`, skip the log scan when the knowledge head still equals the base revision, since no commit could exist.
- **D6 Light `/v1/instance`.** Return the head plus the cheap fail-closed conditions: restore guard, pending operations, journal reachable. Keep full readiness on `/v1/readyz`. Owner-visible API behavior is unchanged: it still answers 503 when unready.

### Phase E — operations

- **E1** Add `c1-admin maintenance optimize`, which runs TerminusDB optimize on both databases. It is documented in `docs/operations`, and `limits.md` records the measured effect.

## Implementation decisions (recorded during implementation)

Design choices are recorded in [ADR-0025](../decisions/ADR-0025-performance.md).

- **B2 dropped.** Memoizing the profile-authority check would save about 3 ms (measured), and M07 requires that check to be fresh.
- **B3 superseded by derived read decisions.** The owner approved this on 2026-10-05. The binding scan turned out to be cheap (35–60 ms for the whole store); the cost was one Check per resource.
- **D4 dropped.** TerminusDB lists documents in layer order, so an in-place snapshot could not equal a fresh listing, and a listing costs about 0.2 s.
- **D6 implemented as concurrent marker reads.** Readiness itself is unchanged.
- **B4 and C2 deferred.** These CPU paths are not significant at the measured sizes once round trips are removed.
- **History** is still about 7 s on the laptop. The cost is TerminusDB `/api/history` itself, which would need a history index (a separate decision).

## Verification

1. Unit: the round-trip budget tests (A1), the cache-invalidation tests (B1: a new commit means new keys; unauthorized IDs are never served), the size-monotonicity property (C1), and the batched-decision equivalence test (D3, the same pattern as `tests/integration/m09a/test_t01_equivalence.py`). `make check`.
2. Full regression on makako: `docs/evidence/M13/run-makako-gate.sh`, 119 cases, with the M07 goldens unchanged. Then the M13 reference phase, `run-reference-phase.sh` (T01–T08 and the bench).
3. M14 benchmark at scale S, plus M if time allows, on makako. Compare against the committed `v1-makako` baseline: fidelity, security and revocation must stay at 1.0 with no quality change; latency is judged against these targets:
   - simple reads ≤ 2 s median at S;
   - `graph-context` 64 KiB ≤ 6 s;
   - no 503 at B2;
   - a 36-replace apply ≤ 60 s;
   - single-create apply ≤ 5 s.
4. Record the round-trip counts before and after per endpoint in the report. `limits.md` is regenerated from the new `bench.json`.
