# ADR-0017 — Data-only software profile, target sets, and source ingestion

**Status:** Accepted for M08 implementation, 2026-09-29.
**Context:** [M08 plan](../milestones/M08.md) D1–D14; PROJECT_SPECIFICATION.md §10; AGENTS.md §7.

## Decision

1. **Data-only profile.** `software` 1.0.0 (`urn:c1:ns:software#`) is
   generated by `scripts/build_software_profile.py`, which writes
   `profiles/available/software/` and its catalog-test copy. The M02
   reservation of the name is lifted.
   - Entity-kind classes reuse the core Entity template: product,
     repository, release, snapshot, capability, symbol, interface
     operation, and test case.
   - Occurrences, runs, configurations, target sets, branch observations,
     coverage, issues, and unresolved references are record-kind classes.
   - Semantic links are ordinary Assertions whose predicate names the
     evidence basis.
2. **Identity.** Canonical IDs are minted and never derived from commit
   IDs, names, or producers.
   - A logical `CodeSymbol` is keyed by repository and SCIP descriptors;
     the package version is excluded.
   - A `SymbolOccurrence` pins that symbol to one snapshot, file Document,
     part, and half-open range with its position encoding.
   - An `InterfaceOperation` is a logical identity, keyed by provider
     product and `operationId`. Each contract version that specifies it
     is linked by `specifiedIn`.

   This refines plan D7. With a versioned operation identity, a client's
   declared `operationId` would have to name every contract version,
   which would assert unverified compatibility. The target set's contract
   member now selects the applicable version.
3. **Target sets** are explicit snapshots, contracts, and configurations,
   independent of the C1 revision. Branches resolve only at an explicit
   `as_of` instant, and the resolution is reported. There is no implicit
   latest.
4. **Formats.** Formats are parsed by the deterministic producer, outside
   the service.
   - A SCIP v0.10.0 subset is read from checked-in JSON generated once by
     pinned scip-python 0.6.6 and scip CLI v0.10.0. Both packed and typed
     ranges are accepted.
   - Files that Python's parser rejects are reported, and their index
     entries are discarded.
   - Only a bounded OpenAPI 3.1.1 subset with `operationId` is mapped.
   - JUnit is limited to one testcase per report, with no DTDs.
   - C1 never runs indexers, tests, or stored commands.
5. **Coverage and completion.** Each producer run is one `prov:Activity`
   plus one `ImportCoverage` per scope touched, written last. Its
   `payloadDigest` covers only that scope's records, so it reveals nothing
   about records in other scopes. Partial runs never delete records.
   Absent coverage means unknown. M08 defines no tombstones.
6. **Idempotency.** A readable coverage record for the same method,
   snapshot, scope, and digest makes a rerun a no-op. Within a run, a
   batch whose first record is already readable was applied atomically
   and is skipped. The idempotency key covers the batch content and base
   revision, so exact retries replay and changed retries never reuse a key.
7. **Read API.** `POST /v1/software/targets/resolve` and
   `POST /v1/software/lookup` evaluate one M05 authorized selection. They
   exist only while the profile is installed.

## Consequences in core (development phase, no migration)

- **Class-checked references.** A profile field whose ranges are all
  registered classes is now a reference. ChangeSet validation and apply
  check that the target exists, is readable by the author, and has one of
  those classes (`C1-CS-013`). A record whose *required* class-ranged
  reference is unreadable is hidden on reads and queries rather than
  returned partially. SHACL `sh:class` can see only the validated batch,
  so a class violation on an IRI outside the batch is deferred to that
  reference check.
- **Profile digests do not depend on load order.** An identical
  redeclaration of another extension's predicate (here `dcterms:source`,
  shared with `batteries`) stays in the profile's own definition. Before
  this change, the install-time and detection-time digests could differ.
- **Profile install recovery.** Recovery no longer adds the installing
  profile's classes twice when its schema and marker were already written.
  It also compares decoded marker records, because stored subdocuments
  carry generated IDs.
- **Batched fetches in ChangeSet apply and validation.** Existence,
  reference, and post-commit checks use one batched fetch per ChangeSet,
  instead of one request per registered class per ID. That per-ID probe
  cost about 1.7 s per ID with 39 classes.

- **Deduplicated authorization decisions per request step.** A
  ChangeSet's validation, approval, apply, and recovery repeated identical
  scope and resource checks. That was about 80 journal reads per record,
  or 631 s for 78 records. `_DecisionMemo` computes each distinct decision
  fresh once per step and reuses it only for identical arguments. It
  re-reads the security journal head at the end and fails closed
  (`security_revision_changed`) if the head moved. It keeps no state
  between requests, so it is not a positive cache.
- **Journal listings keyed by data version.** A pending-operation check
  used to download the whole workflow journal. The journal now keeps its
  last full listing together with the TerminusDB data version the backend
  served it at. It reuses the listing only when a fresh head read returns
  that exact version. A data version identifies content, so any write
  forces a new listing, and callers receive copies.
- **Retry of read-only GraphQL queries (refines M07 D21).** D21 retries a
  disconnected TerminusDB request once only for GET. The batched fetch
  sends GraphQL queries as POST, and one such query was dropped during an
  M08 integration load. The single retry now also applies to a POST to
  `/api/graphql/` whose JSON body is exactly one query operation.
  Mutations, other POST/PUT/DELETE requests, and requests with any other
  body are still never retried. Unit tests cover both sides. The owner
  may revert this refinement.
- **Documentation applicability declarations.** A documentation copy at
  snapshot S declares `describesSnapshot` for S and for the listed
  snapshots of other repositories, never for other snapshots of its own
  repository.

## Rejected alternatives

- **Parsing SCIP in the service.** Rejected: it would be a runtime dependency with no benefit, and the owner chose checked-in JSON.
- **Deriving snapshot IDs from commit IDs.** Rejected: a duplicate check could then reveal a hidden snapshot.
- **One whole-run coverage digest.** Rejected: its value depends on hidden records.
