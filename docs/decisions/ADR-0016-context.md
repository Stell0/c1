# ADR-0016 — Deterministic context selection and rendering

**Status:** M07 implementation decision under the owner's authorization. The M07 report records which acceptance checks have actually passed.

## Context

C1 must return immediately usable context from shared knowledge while preserving independent authorization, provenance, qualifiers, source versions, conflicts, and deterministic behavior. The M07 roadmap requires the cross-project battery case without changing exact keyword semantics or adding an AI dependency.

M06 is verified. It defines flat DocumentParts, exact Unicode text and digest behavior, selector checks against source revisions, code excerpt declarations, safe Markdown escaping, and no remote fetch. Citation lookup uses generic authorized resource reads. The approved M07 implementation starts at `7c1c7e67ad9e4b7ab49a6fbd4749ef9cdce77ad2`; its initial approved plan commit is `29ddc193cd28ff777b62daf21caea35e0b83f6d5`.

## Decision

The Context Builder is a read-only service behind `POST /v1/context`. It uses the existing authenticated APIs and one authorized selection. It does not create writes, infer facts, summarize with a model, search semantically, or fetch external content.

Profiles are strict JSON data under a trusted local catalog. They declare versioned anchor and target types, a controlled topic scheme, typed ordered path steps, fact and qualifier predicates, fields, role types, measurement linkage, required qualifiers, and fixed rendering sections. Profiles contain no executable expressions, prompts, or remote imports. Startup rejects invalid catalog entries and readiness fails closed; a request cannot cause an implicit fallback or hot-load an untrusted profile.

Typed paths execute step by step using M05's one-edge-per-step traversal bound. Each step checks its own predicate, direction, and target types. Flattening all step predicates into one predicate allowlist is not equivalent and is prohibited. Topic and label resolution sees only the authorized candidate set. A Concept whose `skos:inScheme` target is unreadable is suppressed as a whole, including its labels. Optional narrower-topic expansion follows only readable, authorized `skos:broader` assertion resources. Topic aliases use exact configured normalization; ordinary exact `ANY/ALL` keyword behavior is unchanged.

The software profile extension remains data-only. Profile-defined custom classes such as Product, Battery, BatteryVersion, Measurement, and Version explicitly use entity kind in their profile declarations. The `measurementRef` property declares Measurement as its class range, so profile validation and interchange reject arbitrary targets. Context interprets their declared role types. The canonical full Entity template stays unchanged; this does not add RDFS inheritance, mutate the core manifest, or change the kind of an existing profile class. Existing exact entity type filters remain exact.

Every relationship remains an independently authorized assertion. A quantity claim references a typed Measurement with an ordinary assertion; units, conditions, and measured-on values are separate assertions about that Measurement. This keeps each relationship and qualifier independently authorizable. The builder reports a disagreement only when the predicate is declared single-valued, known valid-time intervals overlap, and units/conditions are comparable. Distinct targets do not establish exclusivity. Unresolved comparisons preserve the claims without claiming they conflict.

Original sources are counted by unique Source resource ID, regardless of source revision. An import count is supported only by explicit `prov:wasGeneratedBy` Activity records that represent import events. Automatic ChangeSet or apply-recording activities do not count as imports or independent corroboration. This preserves provenance without treating repeated processing of one source as new evidence.

A document excerpt is citable only through an explicit readable Document-to-Source assertion and an independently readable evidence, source, document, and part chain. M06 selector validation and source revision semantics still apply. Evidence and Document source revisions must match before the part can be cited. The Source version and Document/evidence version remain separate fields. If a dependency is missing or unreadable, the citation and excerpt are omitted without revealing why. All IDs remain resolvable through the existing generic authorized resource API; no citation-only singular routes are introduced.

Markdown citations are escaped renderings of structured citation values. The renderer never verifies citations by searching for a raw substring in source text, and it emits no active link. Structured and Markdown outputs derive from the same selection. Budgeting counts the complete Markdown UTF-8 body, including variable metadata, source text, bounds, footer, and the current signed cursor. The structured JSON is parity output, not the wire-size budget. The builder picks the longest contiguous prefix of complete units; an oversized first unit returns 422 with the minimum required budget. It never returns a cursor that makes no progress.

Continuation rebuilds the authorized selection and checks a semantic checkpoint over complete prefix unit content, the full anchor/topic resolution and matching dependencies, and their relevant current bindings. Primary labels and type lists use stable canonical ordering so equivalent reads do not drift from unordered source records. It finalizes the authorization/workflow head within each request. A change to the selected prefix or a revocation requires restart. An unrelated later change that does not affect the selected prefix need not invalidate continuation. Signed cursor token bytes are volatile because expiry and HMAC change; content order and decoded position/checkpoint are the deterministic contract.

## Standards and evidence

The profile uses established vocabulary where it expresses the semantics: SKOS for topic concepts and labels, PROV-O for attributed import activities, and Dublin Core Terms for the explicit document source relation. The synthetic `measurementRef` term provides a profile-local, independently authorizable link from a quantity assertion to its typed Measurement record; it avoids overloading literal qualifiers or embedding measurement structure in a claim. Fixture-specific types and predicates remain in the fixture profile.

References consulted for the mapping are the [SKOS Reference](https://www.w3.org/TR/skos-reference/), [PROV-O](https://www.w3.org/TR/prov-o/), and [Dublin Core Terms](https://www.dublincore.org/specifications/dublin-core/dcmi-terms/). These vocabularies define terms; they do not prove application behavior. The [M06 report](../milestones/M06-report.md) is the verified source contract. M07 runtime and authorization claims are established only by the executed checks recorded in [M07 report](../milestones/M07-report.md).

## Review refinements

The focused review found and corrected seven gaps: suppress a Concept when its scheme is unreadable; require matching Document/Evidence revisions; constrain `measurementRef` to Measurement; authorize each `skos:broader` assertion used for expansion; bind cursor checkpoints to full selector resolution and matching dependencies; sort primary labels and type lists canonically; and make cursor rendering's Markdown byte overhead stable. Fixture expected templates bind producer placeholders to authenticated producer principals, while actual `attributed_to` values remain intact. The two M-B3 values use the same known overlapping validity and comparable units/conditions. The fixture installs its `topics` and `batteries` profiles through separate ordinary schema ChangeSets; the design does not assume M04 supports applying multiple schema profiles in one ChangeSet. A shared operation-group validator enforces one-profile installation at API creation, API edit, and persisted-model validation, with three boundary regression cases. These changes do not imply immutable complete response bytes across cursor expiry.

The original fixture load submitted both profile installs in one ChangeSet. Existing M04 apply behavior selected the first operation, installing `topics`; the subsequent fixture ChangeSet failed validation because `hasInstrument` was not yet declared by `batteries`. That partial history is preserved as observed. The loader now installs one profile per ChangeSet and has an explicit resume path; it does not rewrite the failed proposal or represent the two profiles as atomically installed.

The fixture's valid entity-kind profiles also exposed a known pure storage mapping error (`C1-ST-004`) for a canonical resource IRI without a UUIDv4 suffix. Fixture IDs are deterministic name-derived UUIDs with UUIDv4 version/variant bits, including the topic-scheme entity; this matches the pinned storage mapping without changing C1 identity semantics. New apply attempts preflight pure storage representation before durable apply intent or provisioning security bindings. A legacy pending attempt is closed only if the mapper reproduces that exact diagnostic, the full receipt log proves no commit receipt, and repeated head checks prove the knowledge head is unchanged. Recovery then fails only bindings provisioned by that attempt and atomically records the failed ChangeSet, operation, and idempotency response. This cleanup does not recheck revoked writer permissions, call FGA, or write knowledge; current-binding and tombstone rules remain unchanged. Any receipt, head change, unavailable/incomplete history, changed binding, or other mapper error leaves the operation unresolved for normal recovery. Already-applied historical multi-profile payloads remain readable for audit; new creation, edit, and application paths enforce the one-profile group. This is a bounded correction discovered by the M07 fixture, not a relaxation of M04 apply guarantees.

### M06 document-history timeout: bounded cohort and preserved security barrier

The retained [M06-T04 timing trace](../evidence/M07/m06-t04-timing-first.json) reproduces `GET /v1/documents/{document_id}/history?limit=1` returning 503 `C1-DC-012` after the 2,000 ms deadline. The [review note](../evidence/M07/history-performance-review.md) records the run and phase measurements. The phase intervals overlap; they are not additive.

For an explicitly pinned batch of at most eight history revisions, the accepted optimization is exactly one fresh, complete current schema/profile-and-all-markers authority check per cohort, not per revision. Do not substitute the initial selection read for this check, or reuse it across requests. Ordinary history records still require mandatory fresh per-resource authorization on every call; that authorization is distinct from the cohort's schema/profile-marker authority check. Run the cohort check and any fallbacks under the shared backend gate of eight. Decode, project, and handle collisions independently for each revision. Start the cohort authority task before content collectors. Return no result until the cohort authority check and every required snapshot have succeeded; on failure or cancellation, cancel and await sibling tasks.

M06 D9's acceptance contract is unchanged. The M07 history-only `AuthorizedSelection.finalize_after` refinement overlaps only the knowledge-head equality precondition, fresh authorization against the original complete permission plan, and initial workflow-head read. Knowledge-head errors take precedence. The final workflow-head read starts only after all three succeed, and publication requires an exact plan/head match. On failure, timeout, or cancellation, await every owned task. Do not cache authorization across requests; ordinary finalization remains unchanged. Do not overlap whole-request `_finish` with the delayed final workflow-head read, which could otherwise let a rescope with unchanged knowledge escape the post-wait security barrier.

## Consequences and limits

A source statement, review label, or disagreement marker does not prove truth. Missing citations do not prove that evidence does not exist. Authorization applies to every dependency and is recalculated on continuation. A budget is measured on the actual Markdown page. Validated unpadded Base64URL cursor tokens use fixed-width inline-code delimiters, so token content does not change Markdown escape overhead. Token expiry/HMAC may still change bytes, so this decision does not claim immutable response bytes across requests. Context profiles are local trusted configuration: changing one requires a service restart and a new request using the new digest.
